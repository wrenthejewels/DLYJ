Technical Methodology

A stage-by-stage walkthrough of the live model: what each step does, which data feeds it, and where the uncertainty still sits.

Run the model →

Overview

The live model asks a narrower question than most AI exposure studies. It does not only ask whether AI overlaps with work in an occupation. It asks what happens to the role after pressure hits the task layer: what work gets cheaper first, what support work weakens because of spillover, what human-owned function still remains, which retained human bundles likely gain share, and whether the role stays coherent.

The current library covers 63 occupations, all with reviewed posting-backed task expansions. The reviewed posting layer now carries 532 rows, and only 3 occupations still sit at the thinnest four-row reviewed tier. GPT task-label benchmark coverage now reaches 62 of those 63; the remaining gap is Business Operations Specialists, All Other, which does not map cleanly to that source. The function layer is also no longer a one-anchor placeholder for the promoted cohort: all 30 promoted occupations now start from two reviewed default function anchors, and 17 of them override the generic role-family primary anchor with a reviewed occupation-specific primary. Remaining uncertainty is now less about blank occupation coverage and more about how dense or mature the evidence is within each occupation.

The runtime follows six stages.

  1. Resolve the occupation. The model maps the user to an O*NET occupation and loads the default role data for that occupation.
  2. Build the role. It loads tasks, functions, default task-to-function links, dependency edges, and when relevant a reviewed role variant baseline.
  3. Apply user edits. The user can add or remove tasks, change the variant, edit function anchors, and add support links or task-to-function links.
  4. Resolve task evidence. The model decides how much direct evidence exists for each task and how much it should trust that evidence.
  5. Score pressure and retention. It scores task difficulty, direct pressure, dependency spillover, retained leverage, and wave timing.
  6. Classify the role. It combines those task and function signals into a fate label, a wave trajectory, a first-pass accession map of shrinking versus growing work bundles, a transition-trigger readout for assistive use versus delegation and compression, a compact seat map of what leaves versus stays versus grows inside the role, and a separate recomposition estimate. The public rebundle labels are then synthesized from the highest-share task text plus linked function anchors, then passed through a small cleanup layer so the user sees a work slice rather than an internal cluster name or an obviously stitched phrase. Those bundle rows also carry a coarse confidence badge plus a short evidence-basis reason so thin proxy-heavy reads do not look as certain as reviewed-task-backed ones.

The input tuple is roughly:

Input tuple
$$x = (\text{occupationId},\ \text{questionnaireProfile},\ \text{seniorityLevel},\ \text{compositionEdits},\ \text{dependencyEdits})$$

The shortest way to think about the model is this: tasks describe how the work gets done, functions describe what the human role is there to own, and the graph describes how pressure moves between tasks. The model needs all three layers because AI can pressure the how without fully replacing the why.

Key terms

  • Task: a concrete unit of work, such as drafting a client memo, reconciling accounts, triaging a support request, or reviewing a contract clause.
  • Function: the human responsibility the role exists to own, such as client stewardship, compliance judgment, technical direction, or issue resolution.
  • Role variant: a reviewed starting baseline for occupations that cover meaningfully different work mixes under one title.
  • Prior: the model's starting estimate before it sees strong task-specific evidence.
  • Shrinkage: the rule that blends a noisy observation toward a broader default instead of trusting thin evidence too strongly.
  • Spillover: pressure on a task because connected tasks become cheaper, smaller, or less necessary.
  • Recomposition: the separate question of how much exposed work is likely to turn into workflow redesign or fewer labor hours.

Those terms matter because the model is intentionally layered. A task can be exposed while the function survives. A function can survive while the role still compresses. A role can compress while recomposition into real headcount change remains slow.

Data sources by model stage

Organized by model function rather than dataset family — the clearest way to see why each source exists.

1. Occupation resolver

  • Feeds: O*NET occupation taxonomy, aliases, and work descriptors.
  • Primary source: O*NET Database v30.1.
  • Why it is used: it is the public backbone that tells the model what occupation the user most closely matches.
  • What it does not do: it does not by itself describe the user's exact task mix or current AI exposure.

2. Role builder

  • Feeds: baseline task inventory, reviewed task additions, dependency edges, function anchors, task-to-function links, and reviewed role variants.
  • Primary sources: O*NET tasks, reviewed job-description expansions, reviewed role-graph expansions, reviewed function-accountability priors, and reviewed role variants.
  • Why they are used: O*NET gives the starting structure, but the reviewed layers repair places where O*NET is too generic, too old, or too flat.
  • What they do not do: they do not directly score AI reachability. They tell the model what the role is made of before scoring starts.

3. Evidence resolver

  • Feeds: task-level AI evidence, benchmark task labels, cluster priors, and occupation priors.
  • Primary sources: the Anthropic Economic Index (2026-01-15 release, the main live-task empirical source, normalized from Claude.ai and first-party API task telemetry with O*NET task classification); reviewed task estimates; mapped task labels from GPTs are GPTs (Eloundou et al., 2023), now covering 62 of the 63 selected occupations; cluster prior tables; and occupation prior tables.
  • Why they are used: the model should use the most specific evidence available for the exact task row, but it still needs explicit fallbacks when direct evidence is thin.
  • What they do not do: benchmark and prior layers are not treated as the same thing as observed task evidence.

4. Runtime labor and adoption context

  • Feeds: outer demand, labor tightness, adoption realization, and recomposition context.
  • Primary sources: BLS OEWS (May 2024, employment counts and median wages), BLS Occupational Projections (2024-2034, projected employment growth and openings), BLS CPS (monthly unemployment series by occupation group), and Census BTOS-derived occupation context built through ACS PUMS sector mix.
  • Why they are used: they help answer how quickly technical pressure is likely to turn into workflow change and labor-market change.
  • What they do not do: they do not directly tell the model whether a task is automatable.

5. Calibration-only checks

  • Feeds: accountability checks, fragmentation checks, and adoption realism checks.
  • Primary sources: BLS ORS (2025 preliminary with 2023 backstop), ACS PUMS (2024 via Census API), and Census BTOS.
  • Why they are used: they test whether the model's structural assumptions look plausible against outside data. ORS pressure-tests accountability and autonomy guardrails. ACS checks whether the model treats an occupation as too uniform or too fragmented relative to observed wage, education, industry, and worker-mix spread.
  • What they do not do: ORS and ACS do not directly score tasks. They pressure-test the model from outside the runtime loop.

6. Benchmark comparison layer

  • Feeds: directional comparison against older AI exposure literature.
  • Primary sources: AIOE (AI Occupational Exposure, 2023), Webb AI Exposure (2020, NBER WP 24762), Brynjolfsson, Mitchell & Rock (SML, AEA P&P 2018), and GPTs are GPTs (Eloundou et al., 2023).
  • Why they are used: they are useful audit references when checking whether the live ranking looks directionally strange.
  • What they do not do: they do not determine the final role-fate label on their own.

How the role builder works

The role builder creates the thing the rest of the model scores. It does not start from a single occupation number. It starts from a structured bundle: tasks, functions, and links between them.

The builder loads the occupation's default task inventory, then adds reviewed task expansions where the public task list is too thin. It also loads function anchors, which are the durable responsibilities the role is there to own, and a task-to-function graph that says which tasks support which functions. For some occupations, the builder also loads a reviewed role variant baseline. For many others, it instead starts from a richer reviewed multi-anchor default without exposing a variant selector. All promoted next-30 occupations now follow that path, so the default role graph starts from two reviewed anchors rather than one flat family default.

Each task family starts with a blend of two share estimates: the cluster's structural share prior and the task inventory's observed share. The model normalizes these into a starting composition:

Baseline blend
$$\tilde s_i = 0.65\, s_i^{\text{cluster}} + 0.35\, s_i^{\text{inventory}}, \qquad s_i^{(0)} = \frac{\tilde s_i}{\sum_j \tilde s_j}$$

That baseline is then filtered through your composition edits. Removing tasks takes them out of the active run; adding tasks puts them in. The model renormalizes both the task shares and the function weights after edits so the active composition always sums to one:

Edited composition
$$\mathcal{T}^{*} = (\mathcal{T}^{(0)} \setminus \mathcal{T}^{-}) \cup \mathcal{T}^{+}, \qquad \mathcal{F}^{*} = (\mathcal{F}^{(0)} \setminus \mathcal{F}^{-}) \cup \mathcal{F}^{+}$$
$$s_i = \frac{\mathbf{1}[i\in \mathcal{T}^{*}]\, \tilde s_i}{\sum_{j \in \mathcal{T}^{*}} \tilde s_j}, \qquad w_f = \frac{\mathbf{1}[f\in \mathcal{F}^{*}]\, \tilde w_f}{\sum_{g \in \mathcal{F}^{*}} \tilde w_g}$$

In plain language, the baseline is just a starting point. The user's edits decide what stays in the active run. Removing a task removes it from scoring. Adding a task inserts it. Changing the variant swaps in a different reviewed starting bundle when the occupation supports that split. Adding a support link tells the model that one task partly exists because another task exists. Adding a task-to-function link tells the model that a task contributes to a more central function, which can increase that task's effective centrality and bargaining weight.

This stage is where the model enforces its first scientific discipline: represent the role before trying to predict the role. If the task mix or function map is wrong, no later evidence layer can fully rescue the output.

How the evidence resolver works

The evidence resolver decides two things for each task: what the best available evidence source is, and how much the model should trust it.

Evidence order

  1. Live task evidence: direct task-level evidence from the Anthropic Economic Index stack.
  2. Reviewed task estimate: a reviewed judgment about the exact task row in the exact occupation.
  3. Benchmark task label: a mapped task label from external literature that is useful but usually broader than the row being scored.
  4. Cluster prior: a family-level default for tasks like this.
  5. Occupation prior: the broadest fallback when task and cluster evidence are both weak.

The important idea is specificity. The model prefers the strongest claim about the exact row it is scoring. A reviewed estimate can outrank a broader benchmark label for that reason. A cluster prior is still useful, but it is a fallback, not proof about the exact task.

Why shrinkage exists

Direct evidence is not always strong enough to trust at face value. The model therefore shrinks thin evidence toward a broader prior:

Shrinkage function
$$\hat\theta = \lambda\,\theta_{\text{observed}} + (1-\lambda)\,\theta_{\text{prior}}$$

λ is the reliability weight. When reliability is high, the task-level evidence carries most of the score. When reliability is low, the model falls back toward the broader default instead of pretending to know more than it does.

Task evidence reliability

For live Anthropic task evidence, the model weights stated confidence by observation volume. Internal stub sources (placeholder rows with no real observation) receive zero reliability:

Task evidence reliability
$$\lambda_{\text{task}} = \operatorname{clamp}\!\left(\text{confidence} \cdot \frac{n_{\text{tasks}}}{n_{\text{tasks}} + 40},\,0.05,\,0.98\right)$$

A task with 40 observations gets roughly half-weight from its own evidence; a task with 400 observations gets roughly 91% weight. For reviewed task estimates, benchmark task labels, and proxy rows, the model uses stated confidence, normalized evidence weight, a source-role multiplier (0.88 for reviewed estimates, 0.76 for benchmark labels, 0.42 for cluster proxies, 0.25 for fallback proxies), and a promotion-status factor.

Task evidence blend gate

Resolved task evidence only affects task difficulty or task pressure when reliability clears a threshold of 0.20. Above that threshold the evidence blend weight ramps linearly up to a cap of 0.85:

Task evidence blend gate
$$w_t^{\text{evidence}} = \begin{cases} 0, & \lambda_{\text{task}} \le 0.20 \\ \operatorname{clamp}\!\left(0.85\cdot\frac{\lambda_{\text{task}}-0.20}{1-0.20},\,0,\,0.85\right), & \lambda_{\text{task}} > 0.20 \end{cases}$$

If a task already clears the stronger task-first baseline gate, the runtime reduces the remaining blend weight by the amount already consumed in that baseline promotion instead of applying the same evidence twice.

Task evidence signal weights

The model computes two weighted signal composites from each task's resolved evidence. The ease signal feeds the difficulty formula; the direct evidence signal feeds the direct-pressure formula:

Task ease signal
$$q_t^{\text{ease}} = 0.65\,\text{automationScore}_t + 0.25\,\text{exposureScore}_t + 0.10\,\text{augmentationScore}_t$$
Task direct evidence signal
$$q_t^{\text{direct}} = 0.50\,\text{automationScore}_t + 0.35\,\text{exposureScore}_t + 0.15\,\text{augmentationScore}_t$$

When more than one promoted task-level source is available, the runtime resolves a weighted task-level consensus using source reliability, evidence weight, and source-role multipliers before applying the blend:

Resolved task evidence
$$\omega_{t,s} = \lambda_{t,s}\cdot \text{evidenceWeight}_{t,s}\cdot m(\text{sourceRole}_s)$$
$$\tilde a_t = \frac{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}\,a_{t,s}}{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}}, \qquad \tilde e_t = \frac{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}\,e_{t,s}}{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}}$$

The resolver only averages over the promoted task-level tiers: live Anthropic evidence, reviewed task estimates, and benchmark task labels. Cluster proxies and fallback proxies remain visible as fallback metadata, but they do not become part of the task-evidence blend itself.

Cluster prior reliability

Cluster prior reliability starts from stated evidence confidence but penalizes sources that rely on internal stubs rather than real observations:

Prior reliability
$$\lambda_{\text{prior}} = \operatorname{clamp}\!\left(\text{confidence} \cdot \rho_{\text{source}},\,0.05,\,0.98\right)$$
$$\rho_{\text{source}} = \begin{cases} 0.55, & \text{stub-only sources} \\ 0.78, & \text{stub + Anthropic mix} \\ 1.0, & \text{no stub sources} \end{cases}$$

From evidence to empirical resistance

Some types of work have historically resisted automation more than others, regardless of what AI can do today. The model captures that as empirical resistance: a score derived from the cluster prior layer that reflects how much a task family has structurally resisted automation so far. Higher resistance means the work has more built-in friction against organizational absorption.

Empirical resistance
$$e_i = \operatorname{shrink}\!\left(\operatorname{avg}(p_i^{\text{partial}},\, p_i^{\text{high}}),\;\theta_{\text{occ}}^{\text{auto}},\;\lambda_{\text{prior}},\;0.25\right)$$
$$R_i = 1 - e_i$$

When cluster-level task evidence has enough coverage and reliability, the model can shift the empirical ease estimate toward the task-first cluster average instead of relying only on the prior layer. The task-first cluster weight activates when coverage exceeds 0.35 and mean reliability exceeds 0.30, up to a maximum weight of 0.90:

Task-first cluster weight
$$w_i^{\text{tf}} = \begin{cases} 0, & \text{coverage} \le 0.35 \text{ or reliability} \le 0.30 \\ \operatorname{clamp}\!\left(\left(0.60\,\hat c_i + 0.40\,\hat r_i\right) \cdot 0.90,\,0,\,0.90\right), & \text{otherwise} \end{cases}$$

Here $\hat c_i$ and $\hat r_i$ are the normalized coverage and reliability after subtracting their thresholds.

Human advantage

Each task family carries a static human advantage score $h_i$ that reflects how much the work type inherently depends on human presence, relationships, or embodied judgment. The current values are:

  • Client interaction: 1.0; Relationship management: 1.0
  • Oversight/strategy: 0.85; Coordination: 0.65
  • Decision support: 0.55; QA/review: 0.45
  • Research/synthesis: 0.35; Analysis: 0.30
  • Documentation: 0.20; Drafting: 0.15
  • Workflow admin: 0.12; Execution/routine: 0.05

The engine first scales this to $0.35h_i$, then applies the human-advantage weight inside the difficulty formula. Human advantage also interacts with function retention in the task-graph adjustment step.

Task-first baseline promotion

When an individual task has high enough direct reliability, it can promote into its own baseline rather than inheriting only the cluster seed. The task-first task weight is source-aware: live task evidence can promote at a lower reliability threshold (0.38) than reviewed estimates (0.42), while benchmark labels face a stricter threshold (0.55) and a lower maximum weight (0.65 vs 1.00). Task mapping confidence also damps the weight so ambiguous mappings do not over-promote:

Task-first task baseline
$$D_t^{(0)} = (1-w_t^{\text{tf}})\,D_{c(t)} + w_t^{\text{tf}}\,(1-q_t^{\text{ease}})$$

where $w_t^{\text{tf}}$ is the task-first task weight and $D_{c(t)}$ is the cluster seed difficulty. If the task does not clear the promotion threshold, $w_t^{\text{tf}} = 0$ and the task inherits the cluster baseline directly.

How your answers enter the model

The questionnaire does not directly choose the final label. It adjusts the conditions around the work. The model uses those answers to estimate how much of the role still needs human ownership, how decomposable the work is, how much trust or sign-off remains, how strong the workflow bottlenecks are, and how readily the surrounding organization can absorb AI into the workflow.

Normalization
$$r_k = \operatorname{clamp}\!\left(\frac{R_k-1}{4},0,1\right), \qquad s = \operatorname{clamp}\!\left(\frac{\text{seniorityLevel}-1}{4},0,1\right)$$

The hierarchy input mainly works through the $s$ term. Higher hierarchy levels tell the model that your version of the occupation carries more sign-off, coordination, stakeholder alignment, and retained human accountability. Lower levels push the same occupation toward more decomposable execution.

Composite signals

The model converts your responses into a structured profile, then derives four composite signals that feed all later scoring stages:

Composite signals
$$\text{functionRetention} = \operatorname{avg}(\text{functionCentrality},\ \text{signoff},\ \text{liability},\ \text{relationshipOwnership})$$
$$\text{capabilitySignal} = \operatorname{avg}(\text{aiObservability},\ \text{workflowDecomposability},\ \text{substitutionRiskModifier})$$
$$\text{couplingProtection} = \operatorname{avg}(\text{functionRetention},\ \text{exceptionLoad},\ \text{dependencyBottlenecks},\ \text{externalTrust})$$
$$\text{adoptionPressure} = \text{organizationalAdoptionReadiness}$$

Friction dimensions

The model also derives five friction dimensions from your profile. These become the user-side input to the cluster friction blending in the difficulty formula:

Friction dimensions
$$f^{\text{exception}}=\text{exceptionAndContextLoad}$$
$$f^{\text{accountability}}=\operatorname{avg}(\text{signoff},\ \text{liability},\ \text{functionCentrality})$$
$$f^{\text{judgment}}=\operatorname{avg}(\text{functionCentrality},\ 1-\text{executionVsJudgmentMix},\ \text{relationshipOwnership})$$
$$f^{\text{document}}=\operatorname{avg}(\text{aiObservability},\ \text{workflowDecomposability})$$
$$f^{\text{tacit}}=\operatorname{avg}(\text{exceptionLoad},\ \text{dependencyBottlenecks},\ \text{externalTrust})$$

The friction weights used in the difficulty formula are: tacit 0.28, judgment 0.26, accountability 0.18, exception 0.15, inverse document intensity 0.13.

Function-layer blending

When the selected occupation has a reviewed function graph, the model blends function-level accountability signals into the questionnaire-derived values before scoring. This anchors the signals to the occupation's actual authority and delegation structure rather than relying on user responses alone:

Function-layer blending
$$\text{functionRetention} \leftarrow 0.72\,\text{functionRetention} + 0.14\,\text{humanAuthorityReq} + 0.14\,\text{bargainingPowerRetention}$$
$$\text{couplingProtection} \leftarrow 0.78\,\text{couplingProtection} + 0.10\,\text{delegabilityGuardrail} + 0.06\,\text{trustReq} + 0.06\,\text{judgmentReq}$$
$$\text{augmentationFit} \leftarrow 0.80\,\text{augmentationFit} + 0.10\,\text{bargainingPowerRetention} + 0.10\,\text{judgmentReq}$$
$$\text{substitutionRiskModifier} \leftarrow 0.82\,\text{substitutionRiskModifier} + 0.10(1-\text{delegabilityGuardrail}) + 0.08(1-\text{humanAuthorityReq})$$

The same blending applies to three friction dimensions: accountability_load, judgment_requirement, and tacit_context_dependence each blend at 0.75 questionnaire / 0.25 function-graph. Occupations without a reviewed function graph skip this step entirely and use the questionnaire signals as-is.

How task difficulty is scored

Task difficulty is the model's estimate of how hard it is for an organization to absorb a task into AI-assisted workflow. It is not the same thing as raw model capability. A task can be technically reachable and still be difficult to hand off because of judgment, tacit context, accountability, or workflow coupling.

Cluster friction profiles

Each task family has a baseline friction profile across five dimensions: exception burden, accountability load, judgment requirement, document intensity, and tacit context dependence. Those baselines are then adjusted by your questionnaire responses using a delta-from-neutral blend:

Friction blending
$$f_i^{d} = \operatorname{clamp}\!\left(f_{\text{profile}}^{d} + (f_{\text{user}}^{d} - 0.5) \cdot 0.30,\,0,\,1\right)$$

The cluster's structural friction profile is the anchor. Your answers can shift each dimension by up to ±0.15 from the baseline. An answer at the midpoint changes nothing; extremes pull the friction up or down.

Friction weights

The five friction dimensions are combined into a single intrinsic friction score using empirically grounded weights:

Task-family friction
$$F_i = 0.28f^{\text{tacit}}_i + 0.26f^{\text{judgment}}_i + 0.18f^{\text{accountability}}_i + 0.15f^{\text{exception}}_i + 0.13(1-f^{\text{document}}_i)$$

The weights are calibrated against external labor market evidence. Dallas Fed research (February 2026) found that wages rise specifically in AI-exposed occupations that require tacit knowledge and experience, while employment falls where those qualities are absent. OECD job-posting analysis (AI-WIPS, November 2024) found that originality, which maps closely to judgment requirement, saw the largest skill demand increase in high-AI-exposure occupations. Together these point to tacit context and judgment as the friction dimensions that actually protect roles in practice. The current weights reflect that: tacit (0.28) and judgment (0.26) together outweigh accountability (0.18).

Difficulty base formula

The cluster-level difficulty score combines four components with the following weights:

Difficulty score (base)
$$D_i = \operatorname{clamp}\!\left(0.40\,F_i + 0.25\,(0.35\,h_i) + 0.25\,R_i + 0.10\,\text{couplingProtection},\,0.02,\,0.98\right)$$

The AUTOMATION_DIFFICULTY_WEIGHTS are: intrinsic friction 0.40, human advantage 0.25, empirical resistance 0.25, coupling protection 0.10.

Task-graph adjustments

After the base difficulty, the model adjusts for task-graph signals. Tasks with high bargaining power or value centrality resist automation, while high AI-support observability and substitution risk lower difficulty:

Difficulty score (task-graph adjustments)
$$D_i \leftarrow \operatorname{clamp}\!\left(D_i + 0.08\,h_i\!\cdot\!\text{functionRetention} + 0.04\,\text{augmentationFit} + 0.10\,B_i + 0.05\,C_i + 0.04\max(0,V_i-0.5) - 0.07\,A_i - 0.08\,\text{substitutionRiskModifier},\,0.02,\,0.98\right)$$

Here $B_i$ is bargaining-power weight, $C_i$ is core-task share, $V_i$ is value centrality, and $A_i$ is AI-support observability.

Criticality boost

Criticality boost
$$D_i \leftarrow \operatorname{clamp}\!\left(D_i + 0.08,\,0.02,\,0.98\right) \quad \text{if task family is role-critical}$$

Task difficulty blend

That cluster-family difficulty is still the baseline. The model then projects it onto each active task row and lets reliable resolved task evidence alter the task's own difficulty:

Task difficulty blend
$$D_t = \operatorname{clamp}\!\left((1-w_t^{\text{evidence}})\,D_{c(t)} + w_t^{\text{evidence}}(1-q_t^{\text{ease}}),\,0.02,\,0.98\right)$$

In plain language, each task starts from its family-level difficulty, then reliable task evidence can push it easier or harder. Lower difficulty means the task is easier to absorb sooner. Higher difficulty means the task keeps more friction.

Wave assignment

After difficulty is scored, each task is placed into an approximate timing bucket:

Wave assignment
$$\text{wave}_t = \begin{cases} \text{current}, & D_t \le 0.35 \\ \text{next}, & 0.35 < D_t \le 0.65 \\ \text{distant}, & D_t > 0.65 \end{cases}$$

Adoption realization and absorption rate

Within each wave, the model estimates an absorption rate: how much of the task family's share is likely to be absorbed into AI-assisted workflows. This is not binary; it captures the realistic pace of organizational uptake.

Adoption realization
$$\text{adoptionRealization} = 0.92 + 0.16\cdot\text{adoptionPressure}$$
Absorption rate
$$a_i = \operatorname{clamp}\!\left(\text{adoptionRealization}\,(1 - 0.3D_i)\,(0.92 + 0.10A_i - 0.06C_i)\,(1 - 0.10\,\text{dependencyBottlenecks})\,(1 - 0.08\,\text{signoff}),\,0.45,\,0.95\right)$$

The absorbed share in the current wave feeds directly into the recomposition layer's workflow compression estimate.

How pressure moves through the role

The model distinguishes between direct pressure and spillover. Direct pressure means AI can reach the task itself. Spillover means the task becomes less necessary because connected tasks are changing.

Task share derivation

Each task's share of the role is derived from its cluster share and its within-cluster time-share prior, then renormalized across the active task set:

Task share
$$s_t^{\text{raw}} = s_{c(t)} \cdot \frac{\text{timeSharePrior}_t}{\sum_{j \in c(t)} \text{timeSharePrior}_j}$$
$$s_t = \frac{\mathbf{1}[t\in \mathcal{T}^{*}]\, s_t^{\text{raw}}}{\sum_{j \in \mathcal{T}^{*}} s_j^{\text{raw}}}$$

Task direct pressure

The baseline direct pressure for each task combines three signals: the complement of difficulty (how easy the task is to absorb), the cluster's absorption rate, and the task's AI-support observability. Reliable task evidence can then blend into the final score:

Task direct pressure
$$p_{t,\text{base}}^{\text{direct}} = \operatorname{clamp}\!\left(0.68(1-D_t) + 0.20\,\alpha_{c(t)} + 0.12\,A_t,\,0,\,1\right)$$
$$p_t^{\text{direct}} = (1-w_t^{\text{evidence}})\,p_{t,\text{base}}^{\text{direct}} + w_t^{\text{evidence}}\,q_t^{\text{direct}}$$

Here $\alpha_{c(t)}$ is the cluster absorption rate and $w_t^{\text{evidence}}$ is the effective direct task evidence weight after accounting for any structural dampening from routine or administrative context.

Spillover

This is why the dependency graph exists. Support work often survives the capability test but fails the dependency test. If upstream work compresses, support tasks can still lose value:

Spillover
$$p_t^{\text{spill}} = \sum_{(t,u)\in \mathcal{D}^{*}} d_{tu}\, p_u^{\text{direct}} \max(V_u,B_u)$$

The term says: spillover rises when a task depends on another task that is under direct pressure and central to the role's value.

Retained leverage

After pressure and spillover are scored, the model asks how much meaningful human work is still left to hold the role together:

Retained leverage
$$L_t = \operatorname{clamp}\!\left(B_t(1-p_t^{\text{direct}})(1-p_t^{\text{spill}}) + 0.10\,\mathbf{1}[t\in \text{core}] + 0.08\,\mathbf{1}[t\in \text{userCritical}] + 0.08\,\mathbf{1}[t\in \text{aiSupport}] + 0.60\,\text{elevationBoost}_t,\,0,\,1\right)$$

Task-derived cluster summaries

After the task table is scored, the model aggregates those task rows back into cluster summaries. The exposed-cluster list, retained-cluster list, and wave cards are all task-derived rather than inherited from a separate pre-task stack:

Task-derived cluster summary
$$\bar p_i^{\text{direct}} = \frac{\sum_{t \in i} s_t\,p_t^{\text{direct}}}{\sum_{t \in i} s_t}, \qquad \bar p_i^{\text{spill}} = \frac{\sum_{t \in i} s_t\,p_t^{\text{spill}}}{\sum_{t \in i} s_t}$$
$$\text{exposedShare}_i = \sum_{t \in i} \text{exposedShare}_t, \qquad \text{retainedShare}_i = \sum_{t \in i} \text{retainedShare}_t$$

Residual role integrity

The role-level residual integrity score combines retained leverage, retained core share, low spillover, and low dependency penalty:

Residual role integrity
$$I_{\text{role}} = \operatorname{clamp}\!\left(0.40\,\bar L + 0.35\min(1,\text{retainedCoreShare}) + 0.15(1-\bar p^{\text{spill}}) + 0.10(1-\text{depPenalty}),\,0,\,1\right)$$

This is the stage where the model becomes a role-transformation model instead of a pure exposure model. It is no longer only asking what AI can do. It is asking what pressure does to the structure of the role.

How the outputs are chosen

The model produces three output layers.

  • Task and function diagnostics: direct pressure, spillover, retained leverage, exposed core share, retained core share, retained accountability strength, retained bargaining power, and role fragmentation risk.
  • Wave and recomposition outputs: current, next, and distant wave timing, plus workflow compression and organizational conversion estimates.
  • Role-fate label: a rule-based classification that maps the structural picture into one of the public outcome labels.

Retained function strength

Retained function strength combines the complement of function exposure pressure, the function-level delegability guardrail, and weighted bargaining:

Retained function strength
$$S_{\text{fn}} = \operatorname{clamp}\!\left(0.42\,(1-p^{\text{fn}}_{\text{exposure}}) + 0.42\,G + 0.16\,\bar B,\,0,\,1\right)$$

Here $p^{\text{fn}}_{\text{exposure}}$ is the weighted function exposure pressure (0.78 direct + 0.22 indirect), $G$ is the delegability guardrail, and $\bar B$ is the weighted bargaining score across tasks.

Retained accountability strength

Retained accountability strength
$$A_{\text{ret}} = \operatorname{clamp}\!\left(0.18\,(1-p^{\text{fn}}_{\text{exposure}}) + 0.20\,G + 0.22\,\text{humanAuthority} + 0.18\,\text{judgmentReq} + 0.12\,\text{trustReq} + 0.10\,\text{regulatoryLiability},\,0,\,1\right)$$

Retained bargaining power

Bargaining power is not just an average of task bargaining weights. It leans more on pressure-adjusted retained task leverage, then blends in function-level bargaining retention, guardrails, and a specialization lift from the adaptation layer. Routine or support-heavy work already under high pressure pulls bargaining down:

Retained bargaining power
$$B_{\text{ret}} = \operatorname{clamp}\!\left(0.40\,\bar L + 0.22\,\text{fnBargaining} + 0.14\,G + 0.10\,\bar B + 0.06\,A_{\text{ret}} + 0.08\,(1-\bar p^{\text{direct}}) + 0.22\,(\sigma-0.50) + 0.22\max(0,\sigma-0.72) - 0.10\,\text{supportHighPressure} - 0.08\,\text{routineHighPressure},\,0,\,1\right)$$

Here $\sigma$ is the specialization context, a blend of knowledge share (0.42), learning intensity (0.33), and adaptive capacity (0.25). The specialization lift means high-knowledge, high-learning roles can retain leverage even when some execution work is exposed. The $\max(0,\sigma-0.72)$ term adds an extra lift for roles above the 72nd percentile of specialization.

Empirical function-context blending

The live runtime adds an outer empirical function-context layer on top of those formulas. ORS structural guardrails feed an accountability context, labor/quality/adaptation signals feed a bargaining context, and ACS heterogeneity plus adaptation structure feed a fragmentation context. These inputs do not replace the reviewed function map. They act as confidence-weighted constraints:

Context blending
$$A_{\text{final}} = (1-w_a)\,A_{\text{ret}} + w_a\,A_{\text{context}}, \qquad w_a \in [0.10,\,0.28]$$
$$B_{\text{final}} = (1-w_b)\,B_{\text{ret}} + w_b\,B_{\text{context}}, \qquad w_b \in [0.10,\,0.28]$$

The blend weight for each context channel scales with the confidence of that channel: $w = 0.10 + (\text{confidence} \times 0.18)$. When no context is available, the runtime uses the authored values directly.

Runtime demand and adoption context

The fate classifier also uses runtime demand and adoption signals. When pre-computed runtime context rows are available, those override the defaults. The fallback formulas are:

Runtime demand and adoption context
$$D_{\text{labor}} = 0.55\,\text{growthNorm} + 0.25\,\text{openingsNorm} + 0.20$$
$$T_{\text{tightness}} = 0.60\,\text{openingsNorm} + 0.20$$
$$M_{\text{demand}} = 0.70\,D_{\text{labor}} + 0.30\,T_{\text{tightness}}$$
$$P_{\text{effective adoption}} = 0.55\,\text{adoptionPressure} + 0.45\,\text{adoptionRealizationContext}$$

The demand expansion signal combines adaptive capacity (0.22), transferability (0.16), learning intensity (0.12), demand expansion context (0.34), and labor tightness (0.16).

What the fate label means

The public fate labels are short descriptions of a structural read, not a claim of perfect foresight. Each label is the model's answer to a different configuration of pressure and retention.

  • AI increases demand for the role: pressure exists, but demand expansion and retained human value dominate.
  • AI-supported role stays intact: AI changes the workflow without breaking the role's core structure.
  • Less execution, more judgment: exposed execution work shrinks while the retained role becomes more judgment-heavy.
  • Splits into execution and oversight tiers: a rare label the model uses only when the role shows real internal bifurcation into lower-authority execution work and a smaller higher-judgment layer.
  • Same work, fewer people: much of the workflow remains, but fewer labor hours are needed.
  • Core role breaks down: pressure reaches too much of the role's structural core for the current seat to remain coherent.
  • Mixed signals, path still unclear: the model sees competing mechanisms with no clear dominant path yet.

Classifier inputs

The fate classifier is not a trained black box. It is a transparent rule set built on the model's upstream signals. The classifier mainly reads: direct exposure pressure, indirect dependency pressure, retained leverage, residual role integrity, exposed versus retained core share, next-wave retained share and coherence, elevated share, demand expansion modifier, retained accountability, retained bargaining power, fragmentation risk, compressibility, delegation likelihood, headcount displacement risk, and function-level differentiation.

High retained leverage, strong next-wave coherence, and low direct pressure push roles toward "AI-supported role stays intact" or "Less execution, more judgment." Strong labor demand can push some roles toward "AI increases demand for the role." Broad exposure plus meaningful displacement risk pull roles toward "Same work, fewer people." The model only uses "Splits into execution and oversight tiers" when the function layer itself shows evidence of real internal separation rather than generic recomposition. When pressure and counterweights stay in real tension, the classifier falls back to "Mixed signals, path still unclear."

Three time mechanisms

The model keeps three different time mechanisms because they answer different questions:

  • Primary displacement wave asks when the main pressure arrives first: current, next, or distant.
  • Wave trajectory asks what the role looks like in each stage: current wave, next wave, and distant wave.
  • Workflow compression and organizational conversion ask how much technical pressure actually turns into real workflow redesign or fewer labor hours.

Those are not interchangeable. A role can feel pressure in the current wave, still retain a coherent next-wave role, and only convert slowly into real headcount change because firms are slow to reorganize around the technology.

Why recomposition is separate

Recomposition is not the same thing as the final label. It is a narrower read on how much exposed work looks compressible and how likely that compression is to turn into real workflow redesign or fewer labor hours. A role can have meaningful recomposition pressure while still keeping a strong human-owned function. The model keeps those questions separate on purpose.

Workflow compression

Workflow compression
$$W_{\text{raw}} = \operatorname{clamp}\!\left(\text{currentWaveAbsorbed}\,(1-0.20\!\cdot\!\text{couplingProtection})\,(1-0.10\!\cdot\!\text{functionRetention}) + 0.14\!\cdot\!\text{routineCompressionSignal},\,0,\,1\right)$$
$$W = 0.68\,W_{\text{raw}} + 0.32\,W_{\text{context}}$$

The context blend ensures that compression is not purely runtime-derived. The occupation-level workflow compression context, built from adaptation structure and routine share, constrains the estimate from the outside.

Organizational conversion

Organizational conversion
$$O_{\text{raw}} = \operatorname{clamp}\!\left(0.30\,P_{\text{eff}} + 0.25(1-\text{couplingProtection}) + 0.20\,\text{currentWaveAbsorbed} + 0.10(1-f^{\text{accountability}}) + 0.08(1-f^{\text{judgment}}) + 0.07\,f^{\text{document}} - 0.05\,\text{signoff} - 0.05\,\text{liability},\,0,\,1\right)$$
$$O = 0.72\,O_{\text{raw}} + 0.28\,O_{\text{context}}$$
Substitution outputs
$$\text{substitutionPotential} = W \cdot O, \qquad \text{substitutionGap} = W - \text{substitutionPotential}$$

The substitution gap is the portion of workflow compression that has not yet converted into real organizational change. A large gap means technical pressure exists, but the organization has not yet restructured around it.

Technical appendix

This appendix collects the most important mathematical objects and explains what the UI does with them.

Role structure

  • Active tasks $\mathcal{T}^{*}$, active functions $\mathcal{F}^{*}$, and active dependency edges $\mathcal{D}^{*}$.
  • Evidence terms: prior score, observed task evidence, reliability weight $\lambda$, and evidence blend weight $w_t^{\text{evidence}}$.
  • Task-scoring terms: difficulty $D_t$, direct pressure $p_t^{\text{direct}}$, spillover $p_t^{\text{spill}}$, and retained leverage $L_t$.
  • Role-level summaries: direct exposure pressure, indirect dependency pressure, residual role integrity, retained accountability strength, retained bargaining power, role fragmentation risk, and recomposition outputs.

TopK task rankings

The walkthrough panels and appendix use task-level rankings to show the most important rows:

Rendered task rankings
$$\text{Derived task layer} = \operatorname{TopK}_t(s_t)$$
$$\text{Direct pressure list} = \operatorname{TopK}_t(s_t \cdot p_t^{\text{direct}})$$
$$\text{Spillover list} = \operatorname{TopK}_t(s_t \cdot p_t^{\text{spill}})$$
$$\text{Retained leverage list} = \operatorname{TopK}_t(\text{retainedShare}_t \cdot L_t)$$
$$\text{Bargaining list} = \operatorname{TopK}_t\left(s_t \cdot \max(B_t,V_t)\right)$$

Edit-impact panel

The page compares your edited composition to the unedited baseline for the same occupation and variant. That edit-impact panel does not change the score. It is an audit layer that shows which high-level metrics moved most, which tasks and functions changed, and whether the evidence mix became more direct-evidence-heavy or more fallback-heavy when you removed tasks, added tasks, changed function anchors, or adjusted task weights.

Audit trace

A separate audit trace panel names the main pressure tasks, spillover tasks, retained tasks, exposed and retained functions, and the direct-evidence rows most responsible for the current readout. It also includes a copyable text summary so the current audit state can be pasted into notes or review docs without re-reading the whole page. At the task-row level, the page explains in plain English whether a task still follows the fallback cluster model or is being pulled by promoted or blended task evidence.

Coverage and confidence

The runtime tracks direct_coverage_ratio (how much of the task graph resolved to task-level evidence rather than proxy fallback) and composite confidence. That matters because the model is designed to say when it is reading a role mostly through direct task evidence and when it is still leaning on broader fallback structure.

What this model does not do

  • It does not output calibrated probabilities. The fate label is a structured read from a rule set, not a forecast distribution. In very thin-evidence cases the runtime explicitly lowers confidence instead of treating fallback-heavy roles as equally certain.
  • It does not have equal evidence coverage everywhere. Some occupations and task families still rely more heavily on fallback priors than others. The current library covers 63 selected occupations.
  • It does not treat user input as ground truth. User edits are powerful, but they still operate inside a reviewed structural model.
  • It does not model every occupation at the same level of function detail. Some occupations already have rich multi-anchor function graphs, while others still use thinner defaults.
  • It does not let calibration sources quietly replace the runtime logic. ORS, ACS, and most of BTOS remain outside the task-scoring loop because they answer different questions. BTOS now contributes to the outer runtime adoption-realization layer through a derived context row, but it still does not drive task automability directly.
  • It does not claim that exposed work automatically becomes job loss. The entire model exists to avoid that shortcut.
  • The classifier is calibrated heuristically against anchor occupations, not trained on a labeled dataset. The wave system's timing layer is now more empirical than before, but it is still partly derived rather than trained on labeled outcomes.
