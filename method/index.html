How the model works

The live model works in six steps.

  1. We anchor you to a mapped occupation from the O*NET database.
  2. The model builds your role from the occupation task inventory, curated task additions (manually reviewed against real job descriptions), function anchors, and for occupations that cover meaningfully different work types, a curated role-variant baseline.
  3. You can edit that role composition by removing or adding tasks by source, adjusting which functions count, optionally switching the recommended role variant when one exists, and optionally declaring support links between tasks or additional task-to-function connections.
  4. Your role-refinement answers convert into a structured profile covering function retention, sign-off requirement, context load, adoption readiness, augmentation fit, and substitution pressure.
  5. The model scores direct AI pressure, dependency spillover, retained leverage, and wave timing across the task graph.
  6. We tune that calibration into a role-fate label, a wave trajectory, and a separate recomposition read.

Under the hood, a formal scoring model drives everything. The input tuple is roughly:

Input tuple
$$x = (\text{roleCategory},\ \text{occupationId},\ \text{questionnaireProfile},\ \text{seniorityLevel},\ \text{compositionEdits},\ \text{dependencyEdits})$$

The simplest mental model is this: tasks describe how the job gets done, while functions describe what the human role is ultimately there to own. AI often pressures the how before it eliminates the why. The model exists to track that transition rather than assuming that exposed tasks automatically mean the whole role disappears.

The editable tasks come from four sources in the role breakdown: O*NET tasks, curated job-description additions, role-review additions, and value-defining functions. For occupations that cover meaningfully different work types, the model recommends a variant baseline that best matches your questionnaire profile and current role mix, while still letting you override it. In stronger cases, switching variants changes both the starting task bundle and the function-anchor mix. Some occupations use a richer default function graph without an explicit variant selector, including software development, graphic design, paralegal support, compliance work, and financial analysis, where the model distinguishes higher-level direction and stewardship from lower-level execution before any edits. The editor shows which functions each selected task mainly supports, and it accepts optional support links when one task mainly exists to enable another. Your role-refinement answers convert into a structured profile before scoring.

What the model looks at

The model does not guess from your title alone. It combines several layers of data from external research and primary observation:

Primary task evidence

  • Anthropic Economic Index (2026-01-15 release) — the main live-task empirical source. Normalized from Claude.ai and first-party API task telemetry with O*NET task classification, collaboration patterns, human-only ability flags, task success rates, and human/AI time estimates. These rows are the highest-priority evidence tier in the scoring model, preserve observation metadata including usage share, and also seed the cluster priors that anchor the baseline difficulty model. The normalized layer currently contains 530 task evidence rows across all 34 modeled occupations.

Structural backbone

  • O*NET Database (v30.1) — occupation taxonomy, task statements, work context, skills, abilities, and job zones. Provides the task inventory that the role is built from.
  • Reviewed task and role-graph expansions — internal task-gap expansions curated from job-description review for occupations underdescribed by O*NET alone, plus task dependency edges and role-function anchors.
  • Reviewed function-accountability priors — manually authored role-family defaults and occupation-specific overrides describing judgment, trust, liability, authority, and bargaining retention at the function level. These are used to build the function graph and the guardrail signals that sit above the task graph, and they can be revised up or down when the calibration layer shows a clear occupation-specific miss.

Labor-market context

  • BLS Occupational Employment and Wage Statistics (May 2024) — employment counts and median wages for occupation context.
  • BLS Occupational Projections (2024–2034) — projected employment growth, openings, and labor-demand context used in the outer runtime demand layer.
  • BLS Current Population Survey — monthly unemployment series by occupation group, used for the labor-market context chart.
  • BLS Occupational Requirements Survey (2025 preliminary with 2023 backstop) — calibration-only structural context for human-retention checks. It doesn’t change task scores directly; it pressure-tests the model’s accountability and autonomy guardrails against observed work requirements.
  • Census ACS 1-Year PUMS (2024 via the Census API) — calibration-only heterogeneity context for fragmentation checks. It doesn’t change task scores directly; it checks whether the model treats an occupation as too uniform or too fragmented relative to observed wage, education, industry, and worker-mix spread within that occupation. It also fed the review queue that identified which occupations needed curated role-variant baselines.
  • Census Business Trends and Outlook Survey (BTOS) (AI supplement snapshot integrated on 2026-03-13) — sector AI-adoption and workflow-change context joined back to occupations through ACS-derived sector mix. It does not change task scores directly, but it now contributes to the outer runtime adoption-realization layer and still remains part of the calibration check for organizational conversion.

Benchmark validation layers

Most of these academic benchmarks validate directional rankings rather than drive live scores directly. The main exception is task-level GPT benchmark labels, which participate as a supporting task-evidence tier in the scoring stack. Each source is normalized to a common occupation or task key and compared against the live exposure stack:

  • AIOE (AI Occupational Exposure, 2023) — occupation-level AI exposure measure including language-modeling-specific and ability-level exposure values.
  • Webb AI Exposure (2020, NBER WP 24762) — patent-based occupation-level AI, robotics, and software exposure measures.
  • Brynjolfsson, Mitchell & Rock (SML, AEA P&P 2018) — suitability for machine learning at the occupation level.
  • GPTs are GPTs (Eloundou et al., 2023) — GPT-4 and human annotations for task-level and occupation-level automation ratings, plus autoScores for Webb, SML, robotics, and software exposure.

User inputs

  • Your task selections, hierarchy level, optional support-link declarations, optional task-to-function link edits, and role-refinement profile.

So the page is not asking only "can AI do this task?" It is also asking "if AI gets good at this work, what happens to the rest of the role around it, and does a coherent human role still remain?"

How task evidence becomes exposure scores

How a role enters the model

When you choose an occupation, the model does not jump straight to one exposure number. It first resolves the occupation from the BLS / O*NET backbone. Then it loads the richer task inventory for that occupation, which starts from O*NET tasks and can be expanded with reviewed posting-backed additions where O*NET is too generic. After that it loads the function layer: the purpose anchors that describe what the role is for, not just what tasks appear on the surface. Only then does it resolve evidence for each task and score pressure, spillover, retained leverage, and role outcome.

The intake path is therefore: occupation → tasks → functions → evidence resolver → task scores → role outcome. That ordering is deliberate. If the occupation or task representation is wrong, no later evidence layer can fully rescue the output.

What the evidence tiers mean

Live task evidence means the model has a direct task-level empirical signal, mainly from the Anthropic Economic Index stack. Reviewed task estimate means the model does not have strong live evidence for that exact task row, but a reviewed task-specific judgment has been made for that task in that occupation. Benchmark task label means an external benchmark source such as GPTs Are GPTs provides a mapped task label that is useful, but usually broader than a reviewed occupation-specific read. Cluster priors are task-family defaults: if the model does not know a task well, it can still use the average behavior of similar task types. Fallback proxies are the broadest defaults, used when the model has to borrow from structure rather than direct task knowledge.

The key distinction is specificity. A reviewed task estimate is narrower than a benchmark label if the review is about the exact task row the engine is scoring. A fallback proxy is broader: it says “tasks like this usually behave this way,” not “we reviewed this exact task and think it behaves this way.” That is why reviewed task estimates rank above fallback proxies, and why a good reviewed task estimate can also outrank a broader benchmark task label.

The source hierarchy is not mainly about whether a source is external or internal. It is about what kind of claim the source supports for the exact task row. The model prefers the best available evidence for that exact row: first direct live evidence, then reviewed task-specific estimates, then benchmark labels, and only then broader structural fallbacks. That is also why the UI labels every task row with its source tier: so you can see when a score is direct, when it is reviewed, and when it is inherited from broader structure.

Evidence layers (technical detail)

The data sources above do not all carry equal weight. The scoring approach is hybrid: it starts from task-family priors for the fallback difficulty layer and adjusts those priors toward an occupation-level exposure baseline. When a task family has strong enough task-level evidence, the model shifts that cluster baseline toward a task-first estimate. When an individual task has high enough direct reliability, it can promote into its own baseline rather than inheriting only the cluster seed.

  1. Task-level evidence tiers — the scorer first resolves the best available task-level evidence from a compiled per-task exposure table that combines Anthropic task assessments, reviewed task estimates, and benchmark labels (including the GPTs Are GPTs dataset). The live precedence is live Anthropic evidence, then reviewed task estimates, then benchmark labels. Those tiers can all affect the live task score when reliability is high enough, and the strongest task rows can become their own baseline source rather than only adjusting a cluster baseline after the fact.
  2. Cluster-level priors — task-family priors carrying partial and high automation likelihood estimates with an evidence confidence score and primary source tags. This is the fallback scoring layer for automation difficulty when cluster-level task evidence is too thin to support the task-first baseline path.
  3. Occupation-level priors — broader occupation exposure priors carrying an overall automation score. A separate occupation adaptation prior feeds personalization and function-layer demand signals later in the run. The occupation exposure prior is the broadest fallback when cluster evidence is weak.

Low-coverage tasks still inherit a cluster-seeded fallback, so this is a hybrid model rather than a universal task-first prior system. Separately, for a small reviewed subset of occupations, the scorer can choose among more than one reviewed baseline role variant before the editable task graph is even scored.

Shrinkage toward prior

Not every task has strong direct evidence. When evidence is thin, the model leans on broader defaults rather than trusting a weak signal. When evidence is strong, the model lets the observation speak for itself. That tradeoff is controlled by a shrinkage function:

Shrinkage function
$$\hat\theta = \lambda\,\theta_{\text{observed}} + (1-\lambda)\,\theta_{\text{prior}}$$

where λ is the evidence reliability score. High reliability means the observation stands on its own; low reliability means it defers to the prior.

Evidence reliability

The model needs to know how much to trust each piece of evidence. A task with hundreds of real observations deserves more weight than one with a handful. A reviewed task-specific judgment deserves more weight than a broad benchmark label mapped from a different context. Reliability is the score that captures that distinction.

Reliability is calculated differently depending on the evidence layer. Cluster-prior reliability affects the fallback baseline difficulty estimate. Task-level evidence reliability determines whether task evidence is allowed to alter cluster baselines, task baselines, task difficulty, and task pressure. The task-first baseline gate is also source-aware and damped by task mapping confidence. Separately, the model maintains a calibration layer using ORS, ACS PUMS, and BTOS to check whether its human-retention, role-heterogeneity, and adoption-realization claims are directionally plausible. ORS and ACS remain calibration-only. BTOS now also contributes to a derived occupation-level runtime adoption-context row, but only in the outer demand/conversion layer, never as a task-automability source.

Task-level evidence reliability depends on source type. For live Anthropic task evidence, the model weights stated confidence by observation volume. Internal stub sources (placeholder rows with no real observation) receive zero reliability:

Task evidence reliability
$$\lambda_{\text{task}} = \operatorname{clamp}\!\left(\text{confidence} \cdot \frac{n_{\text{tasks}}}{n_{\text{tasks}} + 40},\,0.05,\,0.98\right)$$

So a task with 40 observations gets roughly half-weight from its own evidence; a task with 400 observations gets roughly 91% weight. For reviewed task estimates, benchmark task labels, and proxy rows, the model instead uses stated confidence, normalized evidence weight, and source-type multipliers. This resolved reliability informs evidence confidence and coverage reporting, can promote high-reliability tasks into a task-first baseline (with stricter promotion for benchmark labels than for live or reviewed task evidence), and once it clears a threshold of 0.20 it can also blend resolved task evidence into the task’s final automation-difficulty and direct-pressure scores.

Task evidence blend gate
$$w_t^{\text{evidence}} = \begin{cases} 0, & \lambda_{\text{task}} \le 0.20 \\ \operatorname{clamp}\!\left(0.85\cdot\frac{\lambda_{\text{task}}-0.20}{1-0.20},\,0,\,0.85\right), & \lambda_{\text{task}} > 0.20 \end{cases}$$

If a task already clears the stronger task-first baseline gate, the runtime reduces the remaining blend weight by the amount already consumed in that baseline promotion instead of applying the same evidence twice.

Task ease signal
$$q_t^{\text{ease}} = 0.65\,\text{automationScore}_t + 0.25\,\text{exposureScore}_t + 0.10\,\text{augmentationScore}_t$$
Task evidence signal
$$q_t^{\text{direct}} = 0.50\,\text{automationScore}_t + 0.35\,\text{exposureScore}_t + 0.15\,\text{augmentationScore}_t$$
Resolved task evidence
$$\omega_{t,s} = \lambda_{t,s}\cdot \text{evidenceWeight}_{t,s}\cdot m(\text{sourceRole}_s)$$
$$\tilde a_t = \frac{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}\,a_{t,s}}{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}}, \qquad \tilde e_t = \frac{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}\,e_{t,s}}{\sum_{s \in \mathcal{S}^{\text{task}}_t} \omega_{t,s}}$$

Here the resolver only averages over the promoted task-level tiers for the task: live Anthropic evidence first, then reviewed task estimates, then benchmark task labels. Cluster proxies and fallback proxies remain visible as fallback metadata, but they do not become part of the task-evidence blend itself.

Cluster prior reliability starts from stated evidence confidence but penalizes sources that rely on internal stubs rather than real observations:

Prior reliability
$$\lambda_{\text{prior}} = \operatorname{clamp}\!\left(\text{confidence} \cdot \rho_{\text{source}},\,0.05,\,0.98\right)$$
$$\rho_{\text{source}} = \begin{cases} 0.55, & \text{stub-only sources} \\ 0.78, & \text{stub + Anthropic mix} \\ 1.0, & \text{no stub sources} \end{cases}$$

From evidence to empirical resistance

Some types of work have historically resisted automation more than others, regardless of what AI can do today. The model captures that as empirical resistance: a score derived from the cluster prior layer that reflects how much a task family has structurally resisted automation so far. Higher resistance means the work has more built-in friction against organizational absorption.

Empirical resistance
$$e_i = \operatorname{shrink}\!\left(\operatorname{avg}(p_i^{\text{partial}},\, p_i^{\text{high}}),\;\theta_{\text{occ}}^{\text{auto}},\;\lambda_{\text{prior}},\;0.25\right)$$
$$R_i = 1 - e_i$$

where pipartial and pihigh are the cluster’s partial and high automation likelihoods, θoccauto is the occupation-level automation score, and λprior is the cluster’s evidence reliability. When cluster evidence is strong, Ri reflects the cluster’s own resistance. When evidence is weak, it falls back toward the occupation average.

Human advantage

Each task family also carries a static human advantage score hi that reflects how much the work type inherently depends on human presence, relationships, or embodied judgment. These are set per cluster type, ranging from 1.0 for client interaction and relationship management down to 0.05 for routine execution. The engine first scales this to 0.35hi, then applies the human-advantage weight inside the difficulty formula. Human advantage also interacts with function retention in the task-graph adjustment step.

Cluster friction profiles

Each task family has a baseline friction profile across five dimensions: exception burden, accountability load, judgment requirement, document intensity, and tacit context dependence. These baselines are adjusted by your questionnaire responses using a delta-from-neutral blend:

Friction blending
$$f_i^{d} = \operatorname{clamp}\!\left(f_{\text{profile}}^{d} + (f_{\text{user}}^{d} - 0.5) \cdot 0.30,\,0,\,1\right)$$

The cluster’s structural friction profile is the anchor. Your answers can shift each dimension by up to ±0.15 from the baseline. An answer at the midpoint changes nothing; extremes pull the friction up or down.

Task-graph signals

The task inventory also contributes four signals per task family: bargaining power weight Bi (how much the task explains why the role exists), core share Ci (proportion of core-criticality tasks), value centrality Vi (how central the task is to the role’s value delivery), and AI support observability Ai (how visible and measurable the task’s output is to AI systems). These are averaged from the individual tasks within each family and feed into the difficulty and pressure formulas documented in subsequent sections.

Evidence confidence at the task level

Each individual task in the role breakdown carries a composite evidence confidence that averages four signals: the cluster’s evidence confidence, the task’s source confidence from the inventory, the direct evidence confidence (if any), and the task-to-cluster mapping confidence. The model also tracks a binary has_direct_evidence flag and a direct_coverage_ratio at the role level, so the page can show how much of your role resolved to task-level evidence rather than proxy fallback. That same task-level reliability decides whether the task gets a difficulty and direct-pressure blend.

How it builds your role

The model starts from the selected occupation's task inventory and a task-family blend. For a small reviewed subset of occupations, it can first choose among more than one reviewed role variant baseline using the questionnaire profile and current role mix. It then links those tasks into one or more reviewed role functions, so the baseline is not just a flat task list. That gives it a default picture of what the role is usually made of and what the role is trying to accomplish before personalization.

That distinction matters. Tasks are the operating layer: drafting, reviewing, coordinating, documenting, analyzing, following up. Functions are the purpose layer: client ownership, decision support, compliance judgment, cross-functional orchestration, accountable delivery. A user could try to reason only at the function level, but functions are too broad to show where pressure starts. The model uses tasks to locate the pressure, then functions to decide whether the human-owned core still survives after those tasks change.

Baseline blend
$$\tilde s_i = 0.65\, s_i^{\text{cluster}} + 0.35\, s_i^{\text{inventory}}, \qquad s_i^{(0)} = \frac{\tilde s_i}{\sum_j \tilde s_j}$$

That baseline is then filtered through your composition edits. Removing tasks takes them out of the active run; adding tasks puts them in; function edits renormalize the role's retained-function mix. The model uses the reviewed baseline task-to-function graph directly rather than treating it as reference-only. Optional support links can add spillover paths that do not exist in the default graph, and optional task-to-function links act as overrides or additions when the default graph misses an important connection. If a curated role variant exists for the occupation, changing the variant changes the starting task/function bundle, and for the stronger reviewed split occupations that can mean activating a different secondary function anchor before any edits. Some occupations use a richer default function graph without an explicit variant selector. Your later edits still win over that baseline.

Edited composition
$$\mathcal{T}^{*} = (\mathcal{T}^{(0)} \setminus \mathcal{T}^{-}) \cup \mathcal{T}^{+}, \qquad \mathcal{F}^{*} = (\mathcal{F}^{(0)} \setminus \mathcal{F}^{-}) \cup \mathcal{F}^{+}$$
$$s_i = \frac{\mathbf{1}[i\in \mathcal{T}^{*}]\, \tilde s_i}{\sum_{j \in \mathcal{T}^{*}} \tilde s_j}, \qquad w_f = \frac{\mathbf{1}[f\in \mathcal{F}^{*}]\, \tilde w_f}{\sum_{g \in \mathcal{F}^{*}} \tilde w_g}$$

In plain English, this is the model's answer to "what is your version of this occupation actually made of?" The extra function layer matters because two roles can have similarly exposed tasks but still differ sharply in whether the human role survives as the accountable core.

Users can change this structure directly. Adding or removing tasks changes what work the role contains. Editing task share changes what matters most. Adding support links changes how pressure can spread through the role. Adding a task-to-function link tells the model that a task contributes to a more central function, which can increase that task's effective centrality, bargaining weight, and sometimes its treatment as core work. But even without custom edits, the default reviewed task-to-function bindings now already affect live scoring.

How your answers matter

The role-refinement layer does not directly output the final verdict. It changes the conditions around the work: how observable the work is, how much of the function must still stay human, how much sign-off or liability remains, how bottlenecked the workflow is, and how quickly an organization could actually embed AI into it.

Normalization
$$r_k = \operatorname{clamp}\!\left(\frac{R_k-1}{4},0,1\right), \qquad s = \operatorname{clamp}\!\left(\frac{\text{seniorityLevel}-1}{4},0,1\right)$$

The hierarchy input mainly works through that s term. Higher hierarchy levels tell the model that your version of the occupation is more likely to carry sign-off, coordination, stakeholder alignment, and retained human accountability. Lower hierarchy levels push the same occupation toward more execution-heavy, more decomposable work. It does not switch you into a different occupation; it changes how the model interprets your version of the selected occupation.

The model captures your role-refinement responses and converts them into a structured profile with fields such as function_centrality, human_signoff_requirement, liability_and_regulatory_burden, relationship_ownership, exception_and_context_load, workflow_decomposability, organizational_adoption_readiness, ai_observability_of_work, dependency_bottleneck_strength, augmentation_fit, and substitution_risk_modifier.

The visible prompts are still simple, but under the hood the important distinction is this: the questionnaire is trying to measure what part of the role stays human-retained even if AI helps with more of the underlying work.

Composite signals
$$\text{functionRetention} = \operatorname{avg}(\text{functionCentrality},\ \text{signoff},\ \text{liability},\ \text{relationshipOwnership})$$
$$\text{capabilitySignal} = \operatorname{avg}(\text{aiObservability},\ \text{workflowDecomposability},\ \text{substitutionRiskModifier})$$
$$\text{couplingProtection} = \operatorname{avg}(\text{functionRetention},\ \text{exceptionLoad},\ \text{dependencyBottlenecks},\ \text{externalTrust})$$
$$\text{adoptionPressure} = \text{organizationalAdoptionReadiness}$$
Friction dimensions
$$f_i = (f^{\text{exception}}, f^{\text{accountability}}, f^{\text{judgment}}, f^{\text{document}}, f^{\text{tacit}})$$
$$f^{\text{exception}}=\text{exceptionAndContextLoad}, \quad f^{\text{accountability}}=\operatorname{avg}(\text{signoff},\ \text{liability},\ \text{functionCentrality})$$
$$f^{\text{judgment}}=\operatorname{avg}(\text{functionCentrality},\ 1-\text{executionVsJudgmentMix},\ \text{relationshipOwnership})$$
$$f^{\text{document}}=\operatorname{avg}(\text{aiObservability},\ \text{workflowDecomposability}), \quad f^{\text{tacit}}=\operatorname{avg}(\text{exceptionLoad},\ \text{dependencyBottlenecks},\ \text{externalTrust})$$

In plain English, the questionnaire tells the model whether AI mainly helps the role, compresses the role, or still leaves a human-retained core because of function, accountability, trust, and messy exceptions.

When the selected occupation has a reviewed function graph, the model blends function-level accountability signals into the questionnaire-derived values before scoring. This anchors the signals to the occupation's actual authority and delegation structure rather than relying on user responses alone.

Those function-level signals are not inferred directly from Anthropic telemetry. They are reviewed function priors first, then summarized mathematically. Each occupation gets one or more function anchors with weighted values for judgment, trust, regulatory burden, human authority, and bargaining retention. The live engine collapses those anchors into weighted averages, blends them into the runtime signals below, and then uses the active task-to-function graph to compute a second live readout of function exposure and retained function strength. For most occupations that still means one main default purpose layer, but some occupations now carry reviewed supplemental anchors even without a separate role-variant selector when one flat function baseline proved too coarse.

Function-layer blending
$$\text{functionRetention} \leftarrow 0.72\,\text{functionRetention} + 0.14\,\text{humanAuthorityReq} + 0.14\,\text{bargainingPowerRetention}$$
$$\text{couplingProtection} \leftarrow 0.78\,\text{couplingProtection} + 0.10\,\text{delegabilityGuardrail} + 0.06\,\text{trustReq} + 0.06\,\text{judgmentReq}$$
$$\text{augmentationFit} \leftarrow 0.80\,\text{augmentationFit} + 0.10\,\text{bargainingPowerRetention} + 0.10\,\text{judgmentReq}$$
$$\text{substitutionRiskModifier} \leftarrow 0.82\,\text{substitutionRiskModifier} + 0.10(1-\text{delegabilityGuardrail}) + 0.08(1-\text{humanAuthorityReq})$$

The same blending applies to three friction dimensions: accountability_load, judgment_requirement, and tacit_context_dependence each blend at 0.75 questionnaire / 0.25 function-graph. Occupations without a reviewed function graph skip this step entirely and use the questionnaire signals as-is.

How the model decides which work is easier to absorb

Not all exposed work gets absorbed at the same speed. A task AI can technically perform might still be hard for organizations to hand off because of accountability requirements, judgment calls, messy exceptions, or sheer institutional inertia. The automation-difficulty score captures that gap between what AI can do in principle and what organizations will actually absorb in practice.

Task-family friction
$$F_i = 0.25f^{\text{accountability}}_i + 0.22f^{\text{judgment}}_i + 0.22f^{\text{tacit}}_i + 0.18f^{\text{exception}}_i + 0.13(1-f^{\text{document}}_i)$$
Difficulty score — base
$$D_i = \operatorname{clamp}\!\left(0.40F_i + 0.25(0.35\,h_i) + 0.25R_i + 0.10\cdot\text{couplingProtection},\,0.02,\,0.98\right)$$
Difficulty score — task-graph adjustments
$$D_i \leftarrow \operatorname{clamp}\!\left(D_i + 0.08\,h_i\cdot\text{functionRetention} + 0.04\,\text{augmentationFit} + 0.10B_i + 0.05C_i + 0.04\max(0,V_i-0.5) - 0.07A_i - 0.08\,\text{substitutionRiskModifier},\,0.02,\,0.98\right)$$
Difficulty score — criticality boost
$$D_i \leftarrow \operatorname{clamp}\!\left(D_i + 0.08,\,0.02,\,0.98\right) \quad \text{if task family is role-critical}$$

h_i is human advantage, R_i is empirical resistance, B_i is bargaining-power weight, C_i is core-task share, V_i is value centrality, A_i is AI-support observability. The base step combines friction, human advantage, empirical resistance, and coupling protection. The second step adjusts for task-graph signals: tasks with high bargaining power or value centrality resist automation, while high AI-support observability and substitution risk lower difficulty. The criticality boost applies only to task families flagged as role-critical. Lower difficulty means the task family is easier to absorb sooner.

That cluster-family difficulty is still the baseline. The model then projects it onto each active task row and lets reliable resolved task evidence alter the task’s own difficulty before wave timing is recomputed.

Task difficulty blend
$$D_t = \operatorname{clamp}\!\left((1-w_t^{\text{evidence}})\,D_{c(t)} + w_t^{\text{evidence}}(1-q_t^{\text{ease}}),\,0.02,\,0.98\right)$$

After that, each task row is placed into an approximate timing bucket: current wave, next wave, or distant wave. The public cluster wave timing is then recomputed from the task-derived cluster summaries rather than copied from the original cluster bundle.

Wave assignment
$$\text{wave}_i = \begin{cases} \text{current}, & D_i \le 0.35 \\ \text{next}, & 0.35 < D_i \le 0.65 \\ \text{distant}, & D_i > 0.65 \end{cases}$$

Within each wave, the model also estimates an absorption rate: how much of the task family's share is likely to be absorbed into AI-assisted workflows. This is not a binary on/off — it captures the realistic pace of organizational uptake.

Adoption realization
$$\text{adoptionRealization} = 0.92 + 0.16\cdot\text{adoptionPressure}$$
Absorption rate
$$a_i = \operatorname{clamp}\!\left(\text{adoptionRealization}\,(1 - 0.3D_i)\,(0.92 + 0.10A_i - 0.06C_i)\,(1 - 0.10\,\text{dependencyBottlenecks})\,(1 - 0.08\,\text{signoff}),\,0.45,\,0.95\right)$$

The task rows use the same basic absorption logic after the task-level difficulty blend, and the cluster-level wave engine then recomputes retained share and elevation from the task-derived cluster bundle. The absorbed share in the current wave feeds directly into the recomposition layer's workflow compression estimate.

How direct risk and spillover work

This is where the model answers the question most people actually have: how much of my role is under pressure, and does the pressure spread beyond the obvious tasks? The model distinguishes between two kinds of pressure:

  • Direct pressure: AI gets good at the task itself.
  • Indirect spillover: the task is not easy to automate, but it exists mainly to support work that is under pressure.

The task graph is how the model captures that second effect. If a support task mainly exists because another task exists, then automating the core task can still reduce the need for the support task.

Task share
$$s_t^{\text{raw}} = s_{c(t)} \cdot \frac{\text{timeSharePrior}_t}{\sum_{j \in c(t)} \text{timeSharePrior}_j}$$
$$s_t = \frac{\mathbf{1}[t\in \mathcal{T}^{*}]\, s_t^{\text{raw}}}{\sum_{j \in \mathcal{T}^{*}} s_j^{\text{raw}}}$$

If you manually edit a task's share in the role graph, the model substitutes your edited share before this normalization step. The interface doesn’t expose separate dominant-task, critical-task, or AI-support toggles, so the model doesn’t apply extra task multipliers beyond your edited share.

Task pressure
$$p_{t,\text{base}}^{\text{direct}} = \operatorname{clamp}\!\left(0.68(1-D_t) + 0.20\alpha_{c(t)} + 0.12A_t,\,0,\,1\right)$$
$$p_t^{\text{direct}} = (1-w_t^{\text{evidence}})\,p_{t,\text{base}}^{\text{direct}} + w_t^{\text{evidence}}\,q_t^{\text{direct}}$$
$$p_t^{\text{spill}} = \sum_{(t,u)\in \mathcal{D}^{*}} d_{tu}\, p_u^{\text{direct}} \max(V_u,B_u)$$

The flow is: current task mix → direct pressure on exposed tasks → spillover into support tasks → surviving leverage among the tasks still tied to core functions. Looking only at functions is too coarse; looking only at tasks overstates replacement. The model uses both layers to ask whether a coherent human-owned role remains after pressure moves through the task map.

After pressure and spillover are scored, the model asks two separate questions. First: how much meaningful human work is still left to hold the role together? That is retained leverage. Second: if that work survives, how scarce or defensible is it? That is bargaining power. A task can help hold the role together without giving the worker much leverage, and a smaller surviving slice can sometimes become more scarce and valuable.

Retained leverage
$$L_t = \operatorname{clamp}\!\left(B_t(1-p_t^{\text{direct}})(1-p_t^{\text{spill}}) + 0.10\mathbf{1}[t\in \text{core}] + 0.60\,\text{elevationBoost}_t,\,0,\,1\right)$$

After the task table is scored, the model aggregates those task rows back into cluster summaries and recomputes wave timing from that task-derived bundle. The exposed-cluster list, retained-cluster list, elevated-cluster list, and wave cards are all task-derived rather than inherited from a separate pre-task stack.

Task-derived cluster summary
$$\bar p_i^{\text{direct}} = \frac{\sum_{t \in i} s_t\,p_t^{\text{direct}}}{\sum_{t \in i} s_t}, \qquad \bar p_i^{\text{spill}} = \frac{\sum_{t \in i} s_t\,p_t^{\text{spill}}}{\sum_{t \in i} s_t}$$
$$\text{exposedShare}_i = \sum_{t \in i} \text{exposedShare}_t, \qquad \text{retainedShare}_i = \sum_{t \in i} \text{retainedShare}_t$$

The task graph also produces role-level summary scores:

  • direct_exposure_pressure
  • indirect_dependency_pressure
  • retained_leverage_score
  • residual_role_integrity
  • exposed_core_share and retained_core_share
  • direct_coverage_ratio, which shows how much of the task graph resolved to task-level evidence rather than proxy fallback

Those task-graph signals do most of the explanatory work on the page. The explanation panel reflects your current run, so editing tasks, functions, support links, or task-to-function links updates it immediately using the same pressure and counterweight logic. The composition editor exposes part of that logic earlier by showing the top function links for each selected task and by letting you add a few support links or task-to-function links when the default graph misses an obvious connection.

How it all comes together

The exposure scores come from the evidence and scoring pipeline earlier on this page. For each task in your role, the model resolves the best available evidence of how automatable that task is, drawing from live Anthropic task assessments, reviewed task estimates, benchmark labels, and cluster-level priors as fallbacks. That evidence is shrunk toward broader occupation priors when it is thin, then combined with friction profiles, human advantage scores, and adoption signals to produce a per-task automation difficulty. Tasks with low difficulty are highly exposed; tasks with high difficulty resist automation. The share-weighted sum of those per-task scores across your role gives the headline exposure number.

But exposure alone does not decide the outcome. A role where 60% of the tasks are exposed can still survive intact if the remaining 40% carries the accountability, judgment, and coordination that hold the position together. A role where only 30% is exposed can still be in trouble if that 30% is the core justification for the job.

So the model layers several signals on top of raw exposure:

  • Retained leverage measures how much meaningful human work is still left after pressure moves through the role. Tasks tied to core functions, protected by guardrails, or elevated by judgment keep more of the role intact than routine support work that merely survives.
  • Bargaining power measures how scarce or defensible that surviving work is. A smaller remaining slice can still have strong bargaining power if it carries rare expertise, authority, or high-value coordination.
  • Dependency structure captures whether exposed tasks pull other tasks down with them. If a support task exists mainly because a core task exists, automating the core task reduces the need for the support task too, even if the support task itself is hard to automate.
  • Your questionnaire profile tells the model how your specific context differs from the default. Adoption readiness, accountability weight, augmentation fit, and substitution pressure all shift the calibration so two people in the same occupation can get different reads.
  • Role integrity asks whether the tasks that survive still form a coherent job. A role can retain leverage on scattered tasks without those tasks adding up to a defensible position.

These signals combine into the summary metrics you see on the results page: direct exposure pressure, retained bargaining power, workflow compression, role fragmentation risk, and residual role integrity. Together they answer a harder question than "can AI do this work?" They answer: after AI absorbs what it can reach, does a coherent, defensible human role remain?

That composite picture is what feeds the fate classifier.

How the final fate label is chosen

Once the model knows what work is exposed, what work spills over, and what work still carries leverage, it maps the role into one of seven organizational outcomes:

  • AI increases demand for the role — AI creates more demand for this role than it displaces.
  • AI-supported role stays intact — AI slots in as a productivity layer, not a structural threat. The role stays intact.
  • Less execution, more judgment — the execution layer shrinks and the retained role becomes more senior and judgment-heavy.
  • Splits into execution and oversight tiers — the role fractures into a cheaper execution tier and a smaller, higher-judgment oversight tier.
  • Same work, fewer people — the work stays, but fewer people are needed to cover it.
  • Core role breaks down — AI reaches the core of what justifies this role existing as a distinct position.
  • Mixed signals, path still unclear — competing pressures with no dominant path yet.

The live classifier is a rule-based tree rather than a trained neural model. It mainly looks at direct exposure pressure, dependency spillover, retained leverage, residual role integrity, exposed versus retained core share, next-wave retained share and coherence, and an outer demand/adoption context layer.

Alongside that headline classifier, the model also computes a function-level transformation layer: function exposure pressure, retained function strength, retained accountability strength, retained bargaining power, delegation likelihood, and headcount displacement risk. Those function metrics do not replace the task graph; they sit above it and help explain whether exposed work is weakening the role's human-owned purpose or only changing how that purpose gets delivered.

Retained accountability strength is not just a readout of trust or regulation. It leans more on delegation guardrails, human authority, and judgment, then adds smaller trust and liability terms. The model is trying to detect roles where a human still owns the real sign-off and decision burden, not just roles that happen to sit in a sensitive environment.

Retained bargaining power is not just a simple average of task bargaining weights. It leans more on pressure-adjusted retained task leverage, then blends in function-level bargaining retention, guardrails, retained accountability, and a specialization lift from the adaptation layer. Routine or support-heavy work already under high pressure pulls the bargaining-power readout down, while high-knowledge, high-learning roles can still retain leverage even when some execution work is exposed.

The reviewed function layer now also makes a clearer distinction between expert work and formal sign-off ownership. Some occupations can remain judgment-heavy, technically scarce, or commercially important while still carrying less final human sign-off than earlier versions of the model assumed. That distinction now shows up mostly in the accountability layer, not by forcing those occupations to lose bargaining power.

The same pattern applies to some sales work. The function layer distinguishes higher-value commercial judgment and account ownership from lower-signoff deal orchestration such as pipeline upkeep, proposal flow, internal coordination, and handoff preparation. The model no longer treats all service-sales work as if it carries the same customer or revenue sign-off burden.

A similar distinction exists in administrative support. The function layer separates lower-authority clerical execution from scheduling, meeting flow, information routing, and follow-up coordination. The model no longer treats all secretary-style work as if it carries one blended administrative guardrail profile.

The function layer can also move the other way. Some support occupations rated too highly in earlier versions because their function defaults implied more scarce leverage than they actually carry. The model corrects that by lowering bargaining retention for support, reconciliation, and analysis-assistance roles when calibration shows those defaults were too generous.

In a few support occupations, that correction now happens structurally instead of only through one flat discount. Bookkeeping work now separates lower-scarcity transaction processing from higher-value reconciliation and exception handling, customer support now separates queue-flow execution from higher-value issue resolution and escalation, and statistical-assistant work now separates data-preparation execution from higher-value statistical support. That makes the bargaining and accountability readouts more specific about which part of the role is actually weakening.

On the task-pressure side, the model treats core workflow-admin and documentation work differently in very routine occupations. Structural routine context does not replace direct task evidence, but it does two things: it raises the baseline pressure for those admin-heavy tasks, and it limits how far direct evidence can pull them down. A narrower office-admin version of that lift also applies to occupations with very high routine share, low people intensity, and lower knowledge share.

The model adds one more clerical check on top of that. If the active role mix is heavily concentrated in workflow-admin, documentation, and execution-routine work, and the function layer says the role carries relatively low authority and low guardrails, the model adds a little more clerical-execution pressure to those same task families. That is how the model represents roles like office clerks more accurately without flattening higher-context admin roles the same way.

The model also keeps three different time mechanisms because they answer different questions:

  • Primary displacement wave asks when the main pressure arrives first: current, next, or distant.
  • Wave trajectory asks what the role looks like in each stage: current wave, next wave, and distant wave.
  • Workflow compression and organizational conversion ask how much technical pressure actually turns into real workflow redesign or fewer labor hours.

Those are not interchangeable. A role can feel pressure in the current wave, still retain a coherent next-wave role, and only convert slowly into real headcount change because firms are slow to reorganize around the technology.

That matters because the model is trying to separate three different ideas that often get confused: tasks that are exposed, roles that get recomposed, and roles whose human-retained function actually weakens enough to collapse.

Runtime demand and adoption context
$$D_{\text{labor}} = 0.55\,\text{growthPctile} + 0.25\,\text{openingsPctile} + 0.20\,\text{inverseUnemploymentPctile}$$
$$T_{\text{tightness}} = 0.60\,\text{openingsPctile} + 0.40\,\text{inverseUnemploymentPctile}$$
$$A_{\text{adoption}} = 0.55\,\text{BTOS adoption} + 0.20\,\text{current AI use} + 0.15\,\text{workflow change} + 0.10\,\text{covered sector share}$$
$$M_{\text{demand}} = 0.70\,D_{\text{labor}} + 0.30\,T_{\text{tightness}}$$
$$P_{\text{effective adoption}} = 0.55\,\text{questionnaire adoption readiness} + 0.45\,\text{occupation adoption realization}$$

High retained leverage, strong next-wave coherence, and low direct pressure push roles toward AI-supported role stays intact or Less execution, more judgment. Strong labor demand can push some roles toward AI increases demand for the role. Stronger adoption realization can also make workflow compression convert into real organizational change more quickly. Large exposed core share and weak retained integrity pull the model toward Same work, fewer people, Splits into execution and oversight tiers, or in the most severe cases Core role breaks down. When the signals conflict, the model falls back to Mixed signals, path still unclear.

Recomposition layer

The page also shows a secondary recomposition panel. This is not the same as the final fate label. It is a narrower estimate of how much exposed work looks technically compressible and how much of that compression may convert into fewer labor hours in firms.

Compression and conversion
$$W = \operatorname{clamp}\!\left(\text{currentWaveAbsorbed}(1-0.20\cdot\text{couplingProtection})(1-0.10\cdot\text{functionRetention}),\,0,\,1\right)$$
$$O = \operatorname{clamp}\!\left(0.30P_{\text{effective adoption}} + 0.25(1-\text{couplingProtection}) + 0.20\text{currentWaveAbsorbed} + 0.10(1-f^{\text{accountability}}) + 0.08(1-f^{\text{judgment}}) + 0.07f^{\text{document}} - 0.05\text{signoff} - 0.05\text{liability},\,0,\,1\right)$$
$$\text{substitutionPotential} = W \cdot O, \qquad \text{substitutionGap} = W - \text{substitutionPotential}$$

Those raw values are then nudged by the task graph. More direct exposure pushes compression higher, while stronger retained leverage and dependency bottlenecks resist full organizational conversion. The model also adds a structural routine-context lift here: occupations with high routine share, low people intensity, and lower job-zone complexity push compression upward more strongly in execution, workflow-admin, documentation, and some drafting-heavy bundles. That is why the recomposition panel can disagree with the final fate label: a role may have technically compressible work and still retain a strong human core.

Why the page looks the way it does

The visible role fate map is built from the underlying task table. Each column answers a different user question:

  • Current role: what takes up the role today?
  • Bargaining power: what most explains why this role exists?
  • Direct pressure: what AI pressures first?
  • Indirect spillover: what shrinks because it depends on exposed work?
  • Retained leverage: what still justifies the role after AI gets better?

Formally, the page ranks tasks by different task-level signals:

Client rankings
$$\text{Current role} = \operatorname{TopK}_t(s_t)$$
$$\text{Bargaining power} = \operatorname{TopK}_t\left(s_t \cdot \max(B_t,V_t)\right)$$
$$\text{Direct pressure} = \operatorname{TopK}_t(s_t \cdot p_t^{\text{direct}})$$
$$\text{Indirect spillover} = \operatorname{TopK}_t(s_t \cdot p_t^{\text{spill}})$$
$$\text{Retained leverage} = \operatorname{TopK}_t(\text{retainedShare}_t \cdot L_t)$$

The page also compares your edited composition to the unedited baseline for the same occupation and variant. That edit-impact panel does not change the score. It is an audit layer that shows which high-level metrics moved most, which tasks and functions changed, and whether the evidence mix became more direct-evidence-heavy or more fallback-heavy when you removed tasks, added tasks, changed function anchors, or adjusted task weights.

A separate audit trace panel names the main pressure tasks, spillover tasks, retained tasks, exposed and retained functions, and the direct-evidence rows most responsible for the current readout. It also includes a copyable text summary so the current audit state can be pasted into notes, review docs, or bug reports without re-reading the whole page. At the task-row level, the page also explains in plain English whether a task still follows the fallback cluster model or is being pulled by promoted or blended task evidence.

What this model does not do

This model is useful, but it is not magic. It emits descriptive confidence and coverage fields, not a full probability distribution over the future.

  • Role-fate confidence is a margin-style score from the current rule set, not a calibrated probability.
  • Task evidence coverage still varies by occupation and task family, even after the reviewed evidence expansion.
  • User task input is now source-bucketed and function-aware, but it is still list-based rather than weighted by rough percentage buckets.
  • Multi-function roles are modeled better than before, but not every occupation yet has a fully reviewed multi-anchor function graph.
  • Adoption context is still weaker than the task layer. Census BTOS now informs the outer runtime adoption-realization layer through an occupation-level derived context row, but it still does not directly drive task automability or task-level evidence resolution.
  • The audit surface is much stronger than earlier versions, but it is still a compact reviewer layer rather than a full provenance browser for every intermediate score.
  • The classifier is calibrated heuristically against anchor occupations, not trained on a labeled dataset.
  • The wave system still exists internally, so role fate currently sits on top of the wave engine rather than fully replacing it.
