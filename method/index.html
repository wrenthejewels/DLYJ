How the model works

This page is a technical walkthrough of the live model. It explains what each stage does, which data feeds it, why that source is used, and where the uncertainty still sits.

Overview

The live model asks a narrower question than most AI exposure studies. It does not only ask whether AI overlaps with work in an occupation. It asks what happens to the role after pressure hits the task layer: what work gets cheaper first, what support work weakens because of spillover, what human-owned function still remains, and whether the role stays coherent.

The runtime follows six stages.

  1. Resolve the occupation. The model maps the user to an O*NET occupation and loads the default role data for that occupation.
  2. Build the role. It loads tasks, functions, default task-to-function links, dependency edges, and when relevant a reviewed role variant baseline.
  3. Apply user edits. The user can add or remove tasks, change the variant, edit function anchors, and add support links or task-to-function links.
  4. Resolve task evidence. The model decides how much direct evidence exists for each task and how much it should trust that evidence.
  5. Score pressure and retention. It scores task difficulty, direct pressure, dependency spillover, retained leverage, and wave timing.
  6. Classify the role. It combines those task and function signals into a fate label, a wave trajectory, and a separate recomposition estimate.

The input tuple is roughly:

Input tuple
$$x = (\text{occupationId},\ \text{questionnaireProfile},\ \text{seniorityLevel},\ \text{compositionEdits},\ \text{dependencyEdits})$$

The shortest way to think about the model is this: tasks describe how the work gets done, functions describe what the human role is there to own, and the graph describes how pressure moves between tasks. The model needs all three layers because AI can pressure the how without fully replacing the why.

Key terms

  • Task: a concrete unit of work, such as drafting a client memo, reconciling accounts, triaging a support request, or reviewing a contract clause.
  • Function: the human responsibility the role exists to own, such as client stewardship, compliance judgment, technical direction, or issue resolution.
  • Role variant: a reviewed starting baseline for occupations that cover meaningfully different work mixes under one title.
  • Prior: the model's starting estimate before it sees strong task-specific evidence.
  • Shrinkage: the rule that blends a noisy observation toward a broader default instead of trusting thin evidence too strongly.
  • Spillover: pressure on a task because connected tasks become cheaper, smaller, or less necessary.
  • Recomposition: the separate question of how much exposed work is likely to turn into workflow redesign or fewer labor hours.

Those terms matter because the model is intentionally layered. A task can be exposed while the function survives. A function can survive while the role still compresses. A role can compress while recomposition into real headcount change remains slow.

Which sources feed which stage

The source map below is organized by model function, not by dataset family. That is the cleanest way to see why each source exists.

1. Occupation resolver

  • Feeds: O*NET occupation taxonomy, aliases, and work descriptors.
  • Primary source: O*NET Database v30.1.
  • Why it is used: it is the public backbone that tells the model what occupation the user most closely matches.
  • What it does not do: it does not by itself describe the user's exact task mix or current AI exposure.

2. Role builder

  • Feeds: baseline task inventory, reviewed task additions, dependency edges, function anchors, task-to-function links, and reviewed role variants.
  • Primary sources: O*NET tasks, reviewed job-description expansions, reviewed role-graph expansions, reviewed function-accountability priors, and reviewed role variants.
  • Why they are used: O*NET gives the starting structure, but the reviewed layers repair places where O*NET is too generic, too old, or too flat.
  • What they do not do: they do not directly score AI reachability. They tell the model what the role is made of before scoring starts.

3. Evidence resolver

  • Feeds: task-level AI evidence, benchmark task labels, cluster priors, and occupation priors.
  • Primary sources: the Anthropic Economic Index, reviewed task estimates, mapped task labels from GPTs are GPTs, cluster prior tables, and occupation prior tables.
  • Why they are used: the model should use the most specific evidence available for the exact task row, but it still needs explicit fallbacks when direct evidence is thin.
  • What they do not do: benchmark and prior layers are not treated as the same thing as observed task evidence.

4. Runtime labor and adoption context

  • Feeds: outer demand, labor tightness, adoption realization, and recomposition context.
  • Primary sources: BLS OEWS, BLS Occupational Projections, BLS occupation-group unemployment series, and BTOS-derived occupation context built through ACS sector mix.
  • Why they are used: they help answer how quickly technical pressure is likely to turn into workflow change and labor-market change.
  • What they do not do: they do not directly tell the model whether a task is automatable.

5. Calibration-only checks

  • Feeds: accountability checks, fragmentation checks, and adoption realism checks.
  • Primary sources: BLS ORS, ACS PUMS, and BTOS.
  • Why they are used: they test whether the model's structural assumptions look plausible against outside data.
  • What they do not do: ORS and ACS do not directly score tasks. They pressure-test the model from outside the runtime loop.

6. Benchmark comparison layer

  • Feeds: directional comparison against older AI exposure literature.
  • Primary sources: AIOE, Webb, SML, and GPTs are GPTs.
  • Why they are used: they are useful audit references when checking whether the live ranking looks directionally strange.
  • What they do not do: they do not determine the final role-fate label on their own.

How the role builder works

The role builder creates the thing the rest of the model scores. It does not start from a single occupation number. It starts from a structured bundle: tasks, functions, and links between them.

The builder loads the occupation's default task inventory, then adds reviewed task expansions where the public task list is too thin. It also loads function anchors, which are the durable responsibilities the role is there to own, and a task-to-function graph that says which tasks support which functions. For some occupations, the builder also loads a reviewed role variant baseline. That matters because one occupation label can cover meaningfully different work shapes.

Edited role structure
$$\mathcal{T}^{*} = (\mathcal{T}^{(0)} \setminus \mathcal{T}^{-}) \cup \mathcal{T}^{+}, \qquad \mathcal{F}^{*} = (\mathcal{F}^{(0)} \setminus \mathcal{F}^{-}) \cup \mathcal{F}^{+}$$

In plain language, the baseline is just a starting point. The user's edits decide what stays in the active run. Removing a task removes it from scoring. Adding a task inserts it. Changing the variant swaps in a different reviewed starting bundle when the occupation supports that split. Adding a support link tells the model that one task partly exists because another task exists.

This stage is where the model enforces its first scientific discipline: represent the role before trying to predict the role. If the task mix or function map is wrong, no later evidence layer can fully rescue the output.

How the evidence resolver works

The evidence resolver decides two things for each task: what the best available evidence source is, and how much the model should trust it.

Evidence order

  1. Live task evidence: direct task-level evidence from the Anthropic Economic Index stack.
  2. Reviewed task estimate: a reviewed judgment about the exact task row in the exact occupation.
  3. Benchmark task label: a mapped task label from external literature that is useful but usually broader than the row being scored.
  4. Cluster prior: a family-level default for tasks like this.
  5. Occupation prior: the broadest fallback when task and cluster evidence are both weak.

The important idea is specificity. The model prefers the strongest claim about the exact row it is scoring. A reviewed estimate can outrank a broader benchmark label for that reason. A cluster prior is still useful, but it is a fallback, not proof about the exact task.

Why shrinkage exists

Direct evidence is not always strong enough to trust at face value. The model therefore shrinks thin evidence toward a broader prior:

Shrinkage
$$\hat\theta = \lambda\,\theta_{\text{observed}} + (1-\lambda)\,\theta_{\text{prior}}$$

λ is the reliability weight. When reliability is high, the task-level evidence carries most of the score. When reliability is low, the model falls back toward the broader default instead of pretending to know more than it does.

What makes evidence reliable

Reliability depends on source type and evidence strength. Live task evidence gets more weight when the observation volume is larger. Reviewed task estimates and benchmark labels are weighted by stated confidence, mapping confidence, and source-type penalties. Stub-only sources are penalized heavily. The result is a model that can say, row by row, whether it is reading a task directly, through a reviewed estimate, or mostly through inherited structure.

That reliability score then affects several later stages: whether the task gets to influence its own baseline, how much direct evidence can alter task difficulty, and how the UI reports evidence confidence.

How your answers enter the model

The questionnaire does not directly choose the final label. It adjusts the conditions around the work. The model uses those answers to estimate how much of the role still needs human ownership, how decomposable the work is, how much trust or sign-off remains, how strong the workflow bottlenecks are, and how readily the surrounding organization can absorb AI into the workflow.

  • Hierarchy level: shifts the role toward more oversight, coordination, sign-off, and stakeholder ownership at higher levels, or toward more decomposable execution at lower levels.
  • Function-retention questions: feed signals such as sign-off, liability, relationship ownership, and judgment load.
  • Workflow questions: feed signals such as decomposability, observability, exception load, and bottleneck strength.
  • Adoption questions: feed signals about augmentation fit, substitution pressure, and organizational readiness.

When the selected occupation has a reviewed function graph, the model blends those user-derived signals with occupation-level function priors. That keeps the model from relying only on generic defaults or only on user self-report. It uses both.

How task difficulty is scored

Task difficulty is the model's estimate of how hard it is for an organization to absorb a task into AI-assisted workflow. It is not the same thing as raw model capability. A task can be technically reachable and still be difficult to hand off because of judgment, tacit context, accountability, or workflow coupling.

The difficulty baseline comes from cluster-level friction profiles and empirical resistance. Those profiles are then adjusted by the user's answers and by function-level guardrails. Reliable task evidence can then pull an individual task away from its cluster baseline when the model has enough reason to trust that move.

Task difficulty blend
$$D_t = \operatorname{clamp}\!\left((1-w_t^{\text{evidence}})\,D_{c(t)} + w_t^{\text{evidence}}(1-q_t^{\text{ease}}),\,0.02,\,0.98\right)$$

In plain language, each task starts from its family-level difficulty, then reliable task evidence can push it easier or harder. Lower difficulty means the task is easier to absorb sooner. Higher difficulty means the task keeps more friction.

That difficulty score is later used for wave timing and absorption. It is one of the most important bridges between evidence and role outcome.

How pressure moves through the role

The model distinguishes between direct pressure and spillover. Direct pressure means AI can reach the task itself. Spillover means the task becomes less necessary because connected tasks are changing.

This is why the dependency graph exists. Support work often survives the capability test but fails the dependency test. If upstream work compresses, support tasks can still lose value.

Spillover
$$p_t^{\text{spill}} = \sum_{(t,u)\in \mathcal{D}^{*}} d_{tu}\, p_u^{\text{direct}} \max(V_u,B_u)$$

The term says: spillover rises when a task depends on another task that is under direct pressure and central to the role's value. The model also computes retained leverage, which is the counterweight signal telling it how much meaningful human work still remains after direct pressure and spillover move through the graph.

This is the stage where the model becomes a role-transformation model instead of a pure exposure model. It is no longer only asking what AI can do. It is asking what pressure does to the structure of the role.

How the outputs are chosen

The model produces three output layers.

  • Task and function diagnostics: direct pressure, spillover, retained leverage, exposed core share, retained core share, retained accountability strength, retained bargaining power, and role fragmentation risk.
  • Wave and recomposition outputs: current, next, and distant wave timing, plus workflow compression and organizational conversion estimates.
  • Role-fate label: a rule-based classification that maps the structural picture into one of the public outcome labels.

The fate classifier is not a trained black box. It is a transparent rule set built on the model's upstream signals. It mainly looks at direct pressure, spillover, retained leverage, residual role integrity, exposed versus retained core share, wave coherence, and outer demand and adoption context. That separation is deliberate. The model first builds the explanation, then chooses the label.

What the fate label means

The public fate labels are short descriptions of a structural read, not a claim of perfect foresight. Each label is the model's answer to a different configuration of pressure and retention.

  • AI increases demand for the role: pressure exists, but demand expansion and retained human value dominate.
  • AI-supported role stays intact: AI changes the workflow without breaking the role's core structure.
  • Less execution, more judgment: exposed execution work shrinks while the retained role becomes more judgment-heavy.
  • Splits into execution and oversight tiers: the role stays real, but it separates into a cheaper execution layer and a smaller oversight layer.
  • Same work, fewer people: much of the workflow remains, but fewer labor hours are needed.
  • Core role breaks down: pressure reaches too much of the role's structural core for the current seat to remain coherent.
  • Mixed signals, path still unclear: the model sees competing mechanisms with no clear dominant path yet.

Why recomposition is separate

Recomposition is not the same thing as the final label. It is a narrower read on how much exposed work looks compressible and how likely that compression is to turn into real workflow redesign or fewer labor hours. A role can have meaningful recomposition pressure while still keeping a strong human-owned function. The model keeps those questions separate on purpose.

Technical appendix

This appendix collects the most important mathematical objects without repeating the full runtime source code.

  • Role structure: active tasks \(\mathcal{T}^{*}\), active functions \(\mathcal{F}^{*}\), and active dependency edges \(\mathcal{D}^{*}\).
  • Evidence terms: prior score, observed task evidence, reliability weight \(\lambda\), and evidence blend weight \(w_t^{\text{evidence}}\).
  • Task-scoring terms: difficulty \(D_t\), direct pressure \(p_t^{\text{direct}}\), spillover \(p_t^{\text{spill}}\), and retained leverage \(L_t\).
  • Role-level summaries: direct exposure pressure, indirect dependency pressure, residual role integrity, retained accountability strength, retained bargaining power, role fragmentation risk, and recomposition outputs.

The runtime also tracks coverage and confidence. That matters because the model is designed to say when it is reading a role mostly through direct task evidence and when it is still leaning on broader fallback structure.

What this model does not do

  • It does not output calibrated probabilities. The fate label is a structured read from a rule set, not a forecast distribution.
  • It does not have equal evidence coverage everywhere. Some occupations and task families still rely more heavily on fallback priors than others.
  • It does not treat user input as ground truth. User edits are powerful, but they still operate inside a reviewed structural model.
  • It does not model every occupation at the same level of function detail. Some occupations already have rich multi-anchor function graphs, while others still use thinner defaults.
  • It does not let calibration sources quietly replace the runtime logic. ORS, ACS, and most of BTOS remain outside the task-scoring loop because they answer different questions.
  • It does not claim that exposed work automatically becomes job loss. The entire model exists to avoid that shortcut.
