How I Built This Model

I did not build this by starting with one grand theory. I kept finding that the current abstraction hid the real mechanism, so I moved one layer lower, kept an explicit fallback, and only then aggregated back upward.

The Starting Problem

I wanted to answer a question that most AI and jobs work does not answer directly: if AI gets better at parts of a role, what happens to the role as an organizational unit?

That is a narrower and more annoying question than "which occupations are exposed to AI?" Exposure is easier to score. It also hides the part I actually cared about. A role can become more productive without shrinking. It can lose routine work and keep a judgment-heavy core. It can split into a cheaper execution tier and a smaller oversight tier. It can also break down. Those are different futures. A single exposure number compresses them into one blur.

So from the start, the object I wanted was not an exposure leaderboard. I wanted a model that could distinguish augmentation, compression, splitting, and collapse.

What I Started From

I did not start from nowhere. The literature on automation and AI exposure already had a clear lineage. Frey and Osborne gave the famous occupation-level automation framing. OECD-style task corrections showed that the unit of analysis matters a lot. Later work like AIOE, Webb, SML, and GPTs are GPTs pushed the field closer to tasks. The Anthropic Economic Index pushed it closer still by using observed AI usage rather than pure theoretical overlap.

Reading that literature gave me two strong beliefs. First, the people doing this work were usually asking a real question, not a fake one. Second, most of the public conversation was using their answers for a different question than the one they had actually measured.

The best exposure papers tell you something important about technological overlap. They do not, on their own, tell you whether a role remains coherent after part of its work gets cheaper.

Why Exposure Scores Are Not Enough

I kept running into the same five failure modes.

  • They flatten core work and support work together. A role exists for some tasks more than others. If the exposed tasks are mostly support work, the role may recompose rather than disappear.
  • They miss spillover. Support tasks can weaken because nearby work changes, even if the support task itself is not easy to automate directly.
  • They miss within-occupation variation. One occupation title can cover several role shapes with very different exposure profiles.
  • They confuse exposed tasks with disappearing seats. A task getting cheaper is not the same event as an organization deciding the role no longer needs a human.
  • They skip adoption friction. Capability, workflow integration, regulation, trust, and labor demand live on different layers of the problem.

That was the main update. The interesting object was not "AI overlap with occupations." The interesting object was "role transformation under pressure."

From Occupations to Clusters

The first model that felt even slightly useful was cluster-level. I broke each occupation into a weighted bundle of task families and gave each family its own difficulty and rough wave timing. That immediately fixed part of the problem. Pressure no longer arrived as one undifferentiated number.

I kept that stage because it was reviewable. A human can inspect a small set of task families. Cluster priors also behave well when direct task evidence is sparse. They were a good scaffold.

But they were still averages. Once I looked closely, the average was doing too much hiding. Tasks inside the same cluster could differ materially in exposure, importance, and retained leverage. So clusters became a fallback layer, not the final layer.

From Clusters to Tasks

The next move was forced by representation. If I wanted to explain why the role exists, I had to know which concrete tasks were doing the work of holding the role together.

O*NET was the natural starting point, but it was not enough by itself. For many occupations it was too generic or too thin. So I added reviewed job-description task expansions, stable internal task IDs, and task attributes such as value centrality, bargaining weight, role criticality, and AI support observability.

That was a conceptual shift. Once tasks became first-class objects, I could stop asking "how exposed is this occupation?" and start asking "which tasks explain why this seat exists, and what happens if those tasks move?" That question is much closer to the one users actually care about.

From Tasks to a Graph

The task layer still assumed tasks were mostly independent. That was false. Real work is coupled. Some tasks feed others, review others, or exist because upstream work exists.

So I added dependency edges. That gave the model a way to distinguish direct pressure from indirect pressure. This was one of the biggest upgrades in the whole build. A support task can survive the capability test and still weaken because the work it supports is shrinking. Without the graph, the model systematically understated that kind of pressure.

I think this is one place where the build became more realistic in a way users can feel immediately. Support work often does not disappear because AI does the support task. It disappears because the workflow around it no longer needs as much support.

Why Tasks Are Still Not Enough

At that point I had tasks, task attributes, and a dependency graph. It was already better than most exposure models. It still missed something important.

Tasks describe how the work gets done. They do not describe what the human role is there to own. That missing layer became the function and accountability layer.

A function is the durable responsibility the role exists to carry: client stewardship, technical direction, compliance interpretation, issue resolution, decision support, and so on. A role can lose a lot of exposed execution work while still retaining a function that the organization wants a human to own.

This was also where I had to get more explicit about institutional structure. Judgment, authority, trust, liability, and delegability are not decorative modifiers. They are part of the mechanism deciding whether a seat survives. Adding the function layer is what turned the project from an exposure model into a role-transformation model.

The key update

The relevant object was not "what percentage of the work can AI do?" It was "what percentage of human-owned responsibility does the role actually lose?" Those are often different numbers.

Making It Real

Two more problems remained. The first was personalization. The second was evidence quality.

Editable structure

I did not want the model to pretend that every user matches the generic occupation bundle. So I made the composition editable. Users can add or remove tasks, switch reviewed variants when they exist, edit function anchors, and declare support links or missing task-to-function links. This was a more honest way to personalize than nudging a few top-level coefficients.

Evidence tiers

I also did not want the public explanation to look task-level while the runtime was still mostly reading from hidden averages. That pushed me toward the current evidence stack: live task evidence first, then reviewed task estimates, then benchmark task labels, then cluster priors, then occupation priors.

The important principle here is specificity. I do not prefer reviewed estimates because they are mine. I prefer them when they make a narrower claim about the exact row being scored than the broader benchmark does. If the model is inheriting a fallback, I want it to say so openly.

Why I did not train an end-to-end predictor

I considered simpler and more fashionable directions. I could have built a more black-box predictor that took occupation features and benchmark signals and produced one final risk number. I rejected that because it would have answered the explanatory question badly. I wanted a model where I could point to the task rows, the function map, the dependency path, and the evidence tier and say: this is why the output moved.

That choice has a cost. The system is more complex than a leaderboard. I think it is the right kind of complexity, because each layer is carrying a different part of the mechanism.

Where It Stands Now

By March 2026, the model had stopped lacking whole conceptual layers. The main work now is to make the existing layers more empirically grounded, less coarse, and easier to audit.

The current runtime is an upward-aggregating pipeline:

  1. Resolve the occupation from the modeled occupation set.
  2. Build an editable task and function graph from reviewed structural data.
  3. Start from cluster-level difficulty as the stable fallback baseline.
  4. Project that baseline onto tasks so tasks become the active scoring unit.
  5. Resolve task-level evidence from the five-tier evidence stack.
  6. Let reliable task evidence alter the task score rather than hiding behind the cluster average.
  7. Propagate dependency spillover across the graph.
  8. Compute retained leverage and function retention after pressure moves.
  9. Aggregate tasks back upward into cluster summaries, waves, and role-level outcomes.
  10. Choose the fate label from the structured signals rather than from a separate opaque score.

What changed my mind recently

Three recent updates were real belief updates rather than routine maintenance.

  • Drafting and documentation were too easy in the model. AEI-backed review showed the friction profiles for those clusters were understating judgment and tacit context. I changed the profiles rather than explaining the miss away.
  • Tacit knowledge and judgment mattered more than I had weighted them. External labor evidence made accountability look too dominant in the difficulty formula. I lowered accountability's relative weight and raised tacit context and judgment.
  • Firm adoption and individual usage were not the same signal. BTOS-derived adoption context and occupation-level AI usage could diverge in either direction. I kept them separate rather than forcing them into one blended story.

What still looks unfinished

  • Task-first coverage is still uneven. Strongly evidenced tasks now behave the way I want. Thin-coverage tasks still depend heavily on fallback priors.
  • Adoption realism is better than it was, but still weaker than the task layer. The outer demand and adoption context is useful and still less grounded than the core task evidence path.
  • Some occupations still have thinner function graphs than I would like. The supplemental-anchor work helped a lot. It did not finish the problem.
  • The audit surface is good and still incomplete. It is much easier to inspect why the model said something. It is not yet a full provenance browser for every intermediate value.
My current read

The next useful work is not inventing another abstraction. It is better evidence coverage, cleaner function maps where the current ones are still flat, and stronger audit surfaces.

Why Calibration Stays Outside Runtime

This was a deliberate design choice. Once I had more outside datasets, the tempting move was to pour them straight into the live score. I decided against that most of the time.

The reason is interpretability. Task automability, organizational adoption, labor demand, and occupational heterogeneity are all real signals. They are not the same signal. If I blend them carelessly, I get a score that looks sophisticated and says less.

So the pattern I try to follow is: use outside data to expose where the model's own layers are wrong, then fix the model at the correct layer. If ORS says the accountability layer is off, I change the accountability layer. If external evidence says a task family is too easy, I change that friction profile. If BTOS says the adoption story is off, I change the outer conversion layer. I do not want score soup.

Design Principles

  • Represent the role before scoring the role If the task mix or function map is wrong, later evidence cannot fully rescue the output.
  • When an abstraction hides the mechanism, move one layer lower That is how the model went from occupations to clusters, clusters to tasks, tasks to a graph, and tasks to functions.
  • Keep explicit fallback tiers Thin evidence should degrade gracefully into broader structure instead of pretending to be precise.
  • Aggregate upward only after the lower layer is coherent Task rows should drive cluster summaries, not the reverse.
  • Prefer auditable mechanisms to opaque elegance I want to be able to point to the row, the link, the function anchor, and the evidence tier that moved the result.
  • Do not confuse exposure with displacement The whole point of the build is to keep those separate for as long as possible.
The compact summary

The model evolved by replacing hidden averages with explicit structure. I expect the next good versions to follow the same pattern.
